## 1. 模块概述

### 1.1 这个模块解决什么

用户拿到今天的训练安排，一组一组练完并记下重量和次数，练完看到一份战报。所有记录可靠地保存下来，换手机也不丢。

### 1.2 设计原则

| 原则 | 含义 |
|---|---|
| **记录不等网络** | 「完成这组」只写本地，立刻生效。同步在后台进行 |
| **原始数据两边都存，计算只在手机上做** | 服务器保存训练和组记录的最终版本；今天练什么、加重建议、PR、战报全部由手机从原始数据现算 |
| **只存事实，不存结论** | 表里存「做了什么」和「当时的目标是什么」，不存「是否达标」「是否 PR」这类判断。判断规则以后可以改，历史数据自动按新规则重算 |
| **漏存的事实补不回来** | 所以宁可现在多存几个字段（完成时刻、当时的目标），也不要以后后悔 |

## 2. 核心概念

| 概念 | 定义 | 例子 |
|---|---|---|
| **训练日** | 方案里的一天，用字母编号 | A 推日、B 拉日、C 腿日 |
| **训练日队列** | 当前方案的全部训练日，按顺序轮转。**不是课表**，不绑定星期几 | A → B → C → A … |
| **一次训练（workout）** | 用户某一天实际进行的训练。**一人一天最多一次** | 2026-10-31 练了 B 拉日 |
| **组（set）** | 一个动作的一组，记实际重量和次数 | 卧推第 2 组 50kg × 10 |
| **动作位置（slot）** | 动作在训练日里排第几（从 0 起）。换动作后位置不变 | 推日第 2 个位置原本是侧平举，换成了前平举 |
| **计划签名（sig）** | `水平|频率|场所|方案id`，标识「当时用的是哪一套计划」 | `some|3|gym|gym-ppl-3` |
| **墓碑** | 删除时不真删，留一条 `done=false` 的记录，通知其他设备 | 取消勾选第 3 组 |

## 3. 用户流程

```
打开小程序 → 「训练」tab（today）
   │
   │  显示：今天练 B 拉日 · 本周 1/3 · 4 个动作 · 约 40 分钟
   │
   ├─ 点主按钮「开始」/「继续」 ──────────┐
   ├─ 点某个动作 ─────────────────────────┤
   │                                      ▼
   │                               记录页（record）
   │                     ┌──────────────────────────────┐
   │                     │ 动作 1/4：引体向上             │
   │                     │ 目标 4 组 × 12 次  上次 …      │
   │                     │ [第1组 ✓][第2组 ✓][第3组][第4组]│
   │                     │                              │
   │                     │ 主按钮：完成第 3 组 · 12 次    │
   │                     └──────────────────────────────┘
   │                          │ 完成一组 → 落库 → 90 秒呼吸环
   │                          │ 全部组完成 → 主按钮变「下一个动作」
   │                          │ 最后一个动作完成 → 「完成训练 · 看战报」
   │                          ▼
   │                     今日战报（report）
   │                       组数 / 吨数 / 时长 / PR / 部位分布 / 本周进度
   │                          │ 「回到首页」
   └──────────────────────────┘
```

中途退出：已完成的组都在；下次进入记录页，自动跳到第一个还没做的动作。

## 4. 数据模型

### 4.1 总览

```
users ─┬─ user_config   设置、换动作、自定义方案（JSON，已有）
       ├─ workouts      一次训练（新增）
       └─ sets          一组记录（已有，补字段）
```

`workouts` 与 `sets` 通过「同一用户 + 同一天」关联，**不建数据库外键**（见 4.4）。

### 4.2 workouts：一次训练（新增）

```sql
create table if not exists workouts (
  user_id      bigint       not null references users(id) on delete cascade,
  date         date         not null,                 -- 训练归属的日期（见 6.5 跨零点）

  plan_key     text         not null default '',      -- 练的是哪个训练日：A|B|C|D；自由训练为空
  plan_name    text         not null default '',      -- 冗余存训练日名称，方案改名后历史不乱
  sig          text         not null default '',      -- 当时的计划签名
  program_id   text         not null default 'auto',  -- 当时用的方案

  started_at   timestamptz  not null,                 -- 开始时刻 = 第一组完成的时刻
  finished_at  timestamptz,                           -- 结束时刻；空 = 没有点「完成训练」

  feel         smallint,                              -- 训练感受 1–5，可空（预留，本期不做界面）
  note         text         not null default '',      -- 备注，≤ 200 字（预留）

  done         boolean      not null default true,    -- false = 墓碑（当天的组全部被取消）
  updated_at   timestamptz  not null,                 -- 客户端写入时刻，LWW 用
  rev          bigint       not null,                 -- 服务端版本号，拉取用
  primary key (user_id, date)
);

create index if not exists workouts_user_rev_idx on workouts (user_id, rev);
```

| 字段 | 谁写 | 何时写 |
|---|---|---|
| `plan_key` `plan_name` `sig` `program_id` | 客户端 | 当天第一组完成时，取当时的训练日与计划 |
| `started_at` | 客户端 | 当天第一组完成时 |
| `finished_at` | 客户端 | 用户点「完成训练 · 看战报」，或今天页点「看战报」时 |
| `feel` `note` | 客户端 | 预留，战报页以后加入口 |
| `done` | 客户端 | 当天最后一组被取消 → `false`；再次完成一组 → `true` |

### 4.3 sets：一组记录（在现有表上补字段）

```sql
create table if not exists sets (
  user_id        bigint        not null references users(id) on delete cascade,
  date           date          not null,
  ex_id          text          not null,
  set_no         smallint      not null,              -- 从 1 开始
  primary key (user_id, date, ex_id, set_no),

  -- 动作信息（冗余，动作库以后改名、调整部位，历史不乱）
  ex_cn          text          not null default '',
  part           text          not null default '',

  -- 归属
  plan_key       text          not null default '',
  sig            text          not null default '',
  slot           smallint,                            -- 新增：动作位置，从 0 起；自由加练为空

  -- 实际做了多少
  weight         numeric(6,2)  not null default 0,
  reps           integer       not null default 0,    -- 计时动作是秒数
  unit           text          not null default 'kg', -- kg | bw | sec
  rir            smallint,                            -- 新增：还剩几次力气，可空（进步可视化用）
  assist         numeric(6,2),                        -- 新增：助力重量，可空（辅助引体等）

  -- 当时的目标（新增）
  target_weight  numeric(6,2),                        -- 页面预填的建议重量
  target_reps    integer,                             -- 计划次数
  target_sets    smallint,                            -- 计划组数

  completed_at   timestamptz,                         -- 新增：这组完成的时刻（只在勾选时写，改数字不变）

  done           boolean       not null default true, -- false = 墓碑
  updated_at     timestamptz   not null,
  rev            bigint        not null
);

-- 已有表的升级（服务启动时自动执行，幂等）
alter table sets add column if not exists slot          smallint;
alter table sets add column if not exists rir           smallint;
alter table sets add column if not exists assist        numeric(6,2);
alter table sets add column if not exists target_weight numeric(6,2);
alter table sets add column if not exists target_reps   integer;
alter table sets add column if not exists target_sets   smallint;
alter table sets add column if not exists completed_at  timestamptz;
```

#### 为什么要新增这几个字段

| 字段 | 不存会怎样 |
|---|---|
| `target_reps` `target_sets` | 「上次做满了没有」现在是拿**当前计划**去比。用户换了方案（推日从 4×10 变成 3×8），历史记录的判断随之改变，加重建议就错了。必须拿**当时的目标**比 |
| `target_weight` | 无法区分「用户采纳了建议」还是「自己改了重量」。进步可视化里「该加了但没加」的判断需要它 |
| `completed_at` | 算不出训练时长、真实组间休息。`updated_at` 改一次数字就会变，不能代替 |
| `slot` | 换过动作后，不知道这一组对应训练日的第几个位置，「训练日完成度」对不上 |
| `rir` `assist` | 进步可视化的估算 1RM 修正与自重负荷（已确认为可选录入） |

#### 字段约束（服务端校验）

| 字段 | 约束 |
|---|---|
| `date` | `YYYY-MM-DD`，真实日期 |
| `ex_id` | 1–16 字符 |
| `set_no` | 1–50 |
| `slot` | 空，或 0–19 |
| `weight` `target_weight` `assist` | 0–1000 |
| `reps` `target_reps` | 0–36000 |
| `target_sets` | 空，或 1–50 |
| `rir` | 空，或 0–10 |
| `unit` | `kg|bw|sec` |
| `ex_cn` ≤ 32 字、`part` ≤ 16、`plan_key` ≤ 8、`sig` ≤ 128 |  |
| `completed_at` `updated_at` | RFC 3339；`updated_at` 必填 |

### 4.4 为什么 workouts 和 sets 之间不加外键

离线时两条记录可能分不同批次到达服务器：先到一组记录，这次训练的行还没到。加外键会让先到的那一批写入失败、整批重试，同步卡住。

两者靠「同一用户 + 同一天」关联，客户端和服务端都以 `sets` 为准：**某天有 `done=true` 的组，就算练过**，即使对应的 workouts 行暂时缺失。

### 4.5 user_config 中与本模块有关的部分（已有）

```jsonc
{
  "profile": { "level": "some", "days": 3, "place": "gym", "programId": "gym-ppl-3" },
  "swaps": { "A:2": "g19" }      // 训练日 A 的第 2 个位置换成了 g19
}
```

设置、换动作、自定义方案仍然整份存为 JSON，不拆表。以后需要运营分析时可以直接查询 JSON 字段，或再拆表。

### 4.6 刻意不建的表

| 不建 | 原因 |
|---|---|
| 训练日队列（plans） | 是「配置 + 包内静态数据」的纯函数，存了就是第二份真相 |
| 动作库、官方方案 | 随小程序包发布；组记录里已冗余存动作名称和部位 |
| 是否达标、是否 PR、加重建议、战报 | 都能从 sets 算出来。规则会改，存下来就过时 |

### 4.7 手机本地存储

本地与服务器是同一个数据模型，一行对一行：

| 键 | 内容 | 说明 |
|---|---|---|
| `lj.sets.YYYY-MM` | 当月组记录 | 按月分 key（技术方案 §7），含待上传的墓碑 |
| `lj.sets.months` | 有数据的月份列表 | |
| `lj.workouts.YYYY` | 当年的训练记录 | 一年最多 366 行，约 40KB，按年分 key 足够 |
| `lj.config` 相关 | 设置、换动作、自定义方案 | 现有 `lj.profile` `lj.swaps` `lj.customPrograms` |
| `lj.plans` | 训练日队列 | **本地缓存**，可随时从配置重新推导，不同步 |
| `lj.sync.*` | 待上传队列、拉取游标 | 同步模块使用 |

本地字段名用 camelCase（`targetReps`、`completedAt`），与接口一致。

## 5. 业务逻辑

### 5.1 今天练什么（F1、F2）

输入：训练日队列、组记录、今天的日期。

```
今天已经有完成的组？
  ├─ 是 → 今天练的就是那个训练日（resumed = true）
  │        训练日 = 今天的组里出现最多的 plan_key
  └─ 否 → 接着上一次训练往下排：
           取「当前计划签名下」最近一次训练的训练日 X
           今天练 = 队列里 X 的下一个（到末尾回到 A）
           从来没练过 → A
```

**为什么接着上一次排，而不是按「本周第几次」排**：一周只练了 2 次的话，按本周次数排会永远在 A/B 之间打转，C 永远轮不到。

**为什么只看当前计划签名**：换了方案以后，旧记录里的「B」和新方案的「B」不是同一个训练日。旧记录不删，但不参与轮转。

老记录没有 `plan_key` 时，按「做过的动作和哪个训练日重合最多」反推。

**本周进度**：

| 项 | 规则 |
|---|---|
| 本周 | 周一到周日 |
| 完成数 | 本周有完成组的**天数**（一天练两次也只算一次） |
| 目标 | 设置里的一周几练 |
| 本周已完成 | 完成数 ≥ 目标。仍然给出下一个训练日，允许加练 |

**今日动作列表**：训练日的动作，应用换动作后展开；每个动作只要今天有一组完成就标为「已练」。

**预计时长**：`max(20, 总组数 × 2.4 分钟，取到 5 的倍数)`。

**首页文案四种状态**：

| 状态 | 条件 | 标题 |
|---|---|---|
| 今天练完了 | 今天所有动作都有完成组 | 今天的推日练完了。 |
| 练了一半 | 今天有完成组，但没练完 | 今天练了 2/4 个动作。 |
| 本周已完成 | 今天没练，本周已达标 | 本周练完了。 |
| 正常 | 其他 | 今天练推日。 |

### 5.2 进入记录页（F3）

| 入口 | 从哪个动作开始 |
|---|---|
| 点某个动作 | 那个动作 |
| 点主按钮 | 第一个今天还没有完成组的动作；全都做过 → 第一个 |
| 今天所有动作都完成 | 主按钮变成「看战报」，直接进战报 |
| 没有计划 | 提示「还没有训练计划」并返回 |

进入时确定**训练日期**（见 6.5），整个记录页内不再变化。

### 5.3 一组的状态与操作（F4–F7）

每一组在页面上有两种状态：

```
         完成（主按钮 / 点勾）
  未完成 ───────────────────────▶ 已完成
    ▲                               │
    └────────── 取消（点勾）────────┘
```

| 操作 | 页面 | 数据 |
|---|---|---|
| **完成一组** | 打勾、杠铃片点亮、震动、开始 90 秒休息 | 写一条组记录：实际重量次数、当时目标、动作位置、`completedAt = 现在`；当天第一组时同时创建 workout |
| **取消一组** | 取消勾、停止休息 | 见下方「取消的规则」 |
| **改未完成组的数字** | 只改页面 | 不写库，完成时一起写 |
| **改已完成组的数字** | 改页面 | 立刻更新这条记录的重量 / 次数；**`completedAt` 不变** |
| **加一组** | 复制最后一组的重量次数，追加在末尾 | 不写库，完成时才写 |
| **主按钮** | 有未完成组 → 完成下一组；全部完成 → 下一个动作；最后一个动作 → 完成训练 | 同上 |

**加组上限 10 组**（页面限制）；服务端允许到 50，给以后的功能留余地。

**取消的规则**（修复现有 bug：现在取消勾选什么都不写，统计仍算这一组）：

| 情况 | 处理 |
|---|---|
| 同步已开启 | 这条记录改为 `done=false`（墓碑），进待上传队列；上传成功后本地物理删除 |
| 同步未开启（纯本地） | 直接物理删除，不需要通知别的设备 |
| 取消的是当天最后一组有效记录 | 当天的 workout 也标为 `done=false` |
| 取消后又重新完成 | 同一个主键覆盖，`done=true`，`completedAt` 取新的时刻 |

取消中间的组（比如 4 组里取消第 2 组）会留下空号，是正常的：组号只是编号，不要求连续。

### 5.4 换动作（F8）

| 规则 | 说明 |
|---|---|
| 候选 | 同部位、同场所的其他动作，**排除当天训练日里已经有的动作**（新规则，见 9.2） |
| 展示 | 最多 6 个 |
| 生效范围 | **永久**：记在配置的换动作表里（键 = `训练日:位置`），以后每次练这个训练日都是新动作 |
| 换回原动作 | 删掉这条替换，不留「换成自己」的记录 |
| 新动作的起始重量 | 有历史 → 按加重建议；第一次做 → 该动作的基线重量 × 水平系数（不能一律 20kg：腿举和弯举差 4 倍） |
| 组数、次数 | 沿用原位置的计划 |
| 已完成的组 | 原动作今天已完成的组**保留**，不会被删除或改名 |
| 计划签名变化时 | 换动作表整体清空（训练日编号的含义变了，旧替换会错位） |

### 5.5 加重建议与上次成绩（F9）

**规则**（渐进超负荷）：

```
找到这个动作「上一次训练」那天的全部完成组（只看负重动作、重量 > 0）
  基准重量 = 那天最重的一组
  组数够了 = 那天完成组数 ≥ 那天的目标组数
  都做满了 = 那天每一组的次数 ≥ 那天的目标次数

组数够了 且 都做满了 → 建议 = 基准 + 一档（下肢 5kg，其他 2.5kg），取 2.5 的整数倍
否则                   → 建议 = 基准（保持）
从没做过                → 计划里的起始重量
```

**本次的改动**：「目标组数 / 目标次数」改为取**那天记录里存的** `targetSets` `targetReps`，不再取当前计划。老记录没有这两个字段时，退回用当前计划（与现在的行为一致）。

**两个专门防住的坑**（保留）：
1. 只勾了 1 组就退出，不算「做满」——必须组数也够
2. 基准取当天最重的一组——用户中途减重，不该把下次的起点拉低

建议值只是**预填**，用户随时可以改。用户改了以后，`targetWeight` 仍记建议值，`weight` 记实际值，两者的差就是「用户没采纳建议」。

**上次成绩的展示**：

| 动作类型 | 文案 |
|---|---|
| 负重 | 上次 50 kg × 10 × 4 组；附一句：今天加 2.5 kg / 上次没做满，今天保持 / 上次只做了 2 组（计划 4 组），今天保持 |
| 自重 | 上次 12 次 × 4 组 |
| 计时 | 上次 45 秒 × 3 组 |
| 第一次 | 第一次做这个动作 |

「上次」统一取那天**最重的一组**（现在自重 / 计时动作取的是第一组，口径不一致，一并修正）。

### 5.6 PR 标记（F10）

| 规则 | 说明 |
|---|---|
| 范围 | 只算负重动作（`unit=kg` 且重量 > 0） |
| 判定 | 今天这个动作的最大重量 > 今天之前的历史最大重量 |
| 第一次做 | **不算 PR**——否则第一个月天天都是新纪录，就不值钱了 |
| 记录页 | 当前重量会破纪录时，杠铃上最后点亮的那一片显示为陶土色 |
| 战报 | 列出今天所有 PR，按提升幅度排序 |

PR 不存表，每次现算。多维度 PR（次数、容量、估算 1RM）归进步可视化模块。

### 5.7 组间休息（F11）

| 规则 | 值 |
|---|---|
| 触发 | 完成一组后自动开始 |
| 时长 | 90 秒（以后可按动作类型配置） |
| 呼吸引导 | 9 秒一个周期：吸 4 秒、呼 5 秒 |
| 结束 | 倒计时到 0、用户点「跳过」、取消勾选、切换动作 |

纯前端功能，不存数据。真实组间休息可以从相邻两组的 `completedAt` 算出。

### 5.8 完成训练与战报（F12）

**完成训练**：

| 入口 | 行为 |
|---|---|
| 记录页最后一个动作做完，点「完成训练 · 看战报」 | 写 `finished_at = 现在` → 进战报 |
| 今天页「看战报」（今天已练完时） | 若 `finished_at` 为空则写入 → 进战报 |
| 一组都没做就点完成 | 提示「还没记录任何一组」，不进战报 |
| 不点完成直接离开 | 训练保持「进行中」，不影响任何统计 |

**训练时长**：

```
时长 = (finished_at 或 最后一组的 completed_at) − started_at + 一组的估算用时（1 分钟）
```

加 1 分钟是因为 `started_at` 是第一组**完成**的时刻，第一组本身的时间要补上。老记录没有 `completed_at` 的，不显示时长。

**战报内容**：

| 项 | 计算 |
|---|---|
| 训练日名称 | workout 的 `plan_name`；没有则「自由训练」 |
| 完成组数 / 计划组数 | 今天完成组数 / 训练日计划的总组数 |
| 动作数 | 今天做过的不同动作数 |
| 吨数 | Σ 重量 × 次数，只算负重动作，换算成吨保留 1 位 |
| 时长 | 见上 |
| PR | 见 5.6 |
| 部位分布 | 按**组数**占比（不按容量：腿的重量大，按容量会把其他部位压得看不见） |
| 本周进度 | 见 5.1 |
| 评语 | 计划全部完成 / 完成了部分 / 没有计划时只说练了几组 |

### 5.9 改设置、换方案对训练记录的影响

| 发生了什么 | 影响 |
|---|---|
| 改水平 / 频率 / 场所，或启用另一个方案 | 计划签名改变 → 训练日队列重新推导；换动作表清空；**今天之后**从新方案的 A 开始 |
| 已有的训练记录 | **一条不删、不改**，统计、PR、加重建议照常使用它们 |
| 今天已经练了一半时换方案 | 今天已完成的组保留；今天剩下的按新方案显示。不建议，但不阻止 |

## 6. 同步与边界情况

### 6.1 同步方式

workouts 与 sets 都走 `POST /api/sync`，与现有协议一致：服务端版本号游标、按行 LWW、墓碑、自然主键幂等（详见契约 §4.2）。

请求和响应各增加一个数组：

```jsonc
// 请求
{ "cursor": 1234, "sets": [...], "workouts": [...], "metrics": [...], "config": null }
// 响应
{ "cursor": 1300, "hasMore": false, "sets": [...], "workouts": [...], ... }
```

`WorkoutRow`：

```jsonc
{
  "date": "2026-10-31", "planKey": "B", "planName": "拉日",
  "sig": "some|3|gym|gym-ppl-3", "programId": "gym-ppl-3",
  "startedAt": "2026-10-31T11:02:15.120Z", "finishedAt": "2026-10-31T11:48:40.002Z",
  "feel": null, "note": "", "done": true,
  "updatedAt": "2026-10-31T11:48:40.002Z"
}
```

`SetRow` 新增字段：`slot` `rir` `assist` `targetWeight` `targetReps` `targetSets` `completedAt`，均可为 `null`。

### 6.2 workouts 的冲突合并

组记录按整行 LWW。workouts 行有两个时间字段，整行 LWW 会丢信息（两台设备同一天都练了，后写的会把较早的开始时刻覆盖掉），所以用**按字段合并**：

| 字段 | 合并规则 |
|---|---|
| `started_at` | 取**较早**的 |
| `finished_at` | 取**较晚**的（任一为空则取非空的） |
| `done` | 不按上传值，由服务端按「这一天是否还有 `done=true` 的组」重新计算（以 sets 为准，见 4.4） |
| 其余字段 | LWW（`updated_at` 新的赢） |

这些规则与到达顺序无关，所以各设备最终结果一致。

### 6.3 上传顺序

同一批上传里，sets 和 workouts 在**同一个事务**里写入。不同批次之间没有顺序要求（不加外键的原因，见 4.4）。

### 6.4 边界情况一览

| # | 情况 | 处理 |
|---|---|---|
| 1 | 没有信号 | 照常记录；恢复网络后自动上传 |
| 2 | 练到一半杀掉小程序 | 已完成的组已落库；再进记录页自动跳到第一个没做的动作 |
| 3 | 两台设备同一天都在记录 | 不同的组各自保留；同一组按 LWW；workout 按字段合并（6.2） |
| 4 | A 设备取消一组，B 设备还没同步 | 墓碑同步到 B 后，B 本地删除这一组 |
| 5 | 本地有未上传的改动时，拉到了这一行的服务端版本 | 先不覆盖本地，等上传后由服务端裁决（契约 §5） |
| 6 | 手机时钟不准 | 拉取用服务端版本号，和时钟无关；LWW 时比服务器快 2 分钟以上的时刻会被夹紧 |
| 7 | 输入了离谱的数字（500kg） | 服务端校验拒绝超过 1000kg 的值；录入时的异常值确认归进步可视化模块 |
| 8 | 同一天同一个动作出现两次 | 会撞主键，见 9.2 |
| 9 | 跨零点训练 | 见 6.5 |
| 10 | 计划被删（自定义方案删除） | 退回自动排；历史记录不受影响 |

### 6.5 跨零点的训练

主键里有日期，跨零点必须有明确规则，否则 23:50 开始、00:20 结束的训练会被拆成两天、两次训练。

**规则**：一次训练的日期 = **它开始的那天**。

| 情况 | 处理 |
|---|---|
| 一直停留在记录页，跨过零点 | 记录页进入时已确定日期，零点后完成的组仍属于前一天 |
| 零点后重新打开记录页 | 前一天的训练「进行中」（未点完成）且最后一组完成在 **3 小时以内** → 继续前一天的训练；否则开始新的一天 |
| 今天页在零点后 | 同上规则判断显示「继续昨天的训练」还是「今天练什么」 |

3 小时足够覆盖一次训练的中途休息，又不会把第二天早上的训练误并进前一晚。

### 7.3 服务端

| 改动 | 说明 |
|---|---|
| `schema.sql` | 新建 `workouts`；`sets` 增加 7 列（`add column if not exists`） |
| `/sync` | 请求和响应增加 `workouts`；校验规则见 4.3 与本节 |
| `push` | workouts 用按字段合并的 upsert（6.2）；同样分配 rev |
| `pull` | 分页从两张表扩展到三张表（按 rev 归并） |

WorkoutRow 校验：`date` 合法；`planKey` ≤ 8、`planName` ≤ 32、`sig` ≤ 128、`programId` ≤ 64；`feel` 空或 1–5；`note` ≤ 200 字；`startedAt` 必填；`finishedAt` 可空且不早于 `startedAt`。

workouts 的 upsert：

```sql
insert into workouts (user_id, date, plan_key, plan_name, sig, program_id,
                      started_at, finished_at, feel, note, done, updated_at, rev)
values (...)
on conflict (user_id, date) do update set
  started_at  = least(workouts.started_at, excluded.started_at),
  finished_at = case
                  when workouts.finished_at is null then excluded.finished_at
                  when excluded.finished_at is null then workouts.finished_at
                  else greatest(workouts.finished_at, excluded.finished_at)
                end,
  -- done 不在这里合并：同一事务里写完 sets 后，按受影响的日期统一刷新（见下方说明）
  plan_key    = case when excluded.updated_at > workouts.updated_at then excluded.plan_key  else workouts.plan_key  end,
  plan_name   = case when excluded.updated_at > workouts.updated_at then excluded.plan_name else workouts.plan_name end,
  sig         = case when excluded.updated_at > workouts.updated_at then excluded.sig       else workouts.sig       end,
  program_id  = case when excluded.updated_at > workouts.updated_at then excluded.program_id else workouts.program_id end,
  feel        = case when excluded.updated_at > workouts.updated_at then excluded.feel      else workouts.feel      end,
  note        = case when excluded.updated_at > workouts.updated_at then excluded.note      else workouts.note      end,
  updated_at  = greatest(workouts.updated_at, excluded.updated_at),
  rev         = excluded.rev;
```

写完 sets 和 workouts 后，在同一事务里刷新受影响日期的 `done`：

```sql
update workouts w set done = exists (
  select 1 from sets s where s.user_id = w.user_id and s.date = w.date and s.done
), rev = $new_rev
where w.user_id = $uid and w.date = any($affected_dates) and w.done is distinct from exists (...);
```

这样「当天的组全部取消 → 这次训练消失」「再完成一组 → 训练恢复」都由服务端保证，与上传顺序无关。`done` 发生变化的行要分配新的 rev，其他设备才能拉到。

## 9. 现有代码需要修正的问题

### 9.1 取消勾选不落库（bug）

`pages/record/index.js` 的 `onToggle` 取消时什么都不写，而 `db.saveSet()` 的 `done: true` 是写死的。页面显示未勾选，统计、战报、PR 仍然算它。按 5.3 修正。

### 9.2 同一天同一个动作出现两次会撞主键

组记录主键是 `(日期, 动作, 组号)`。如果训练日里两个位置是同一个动作（比如把侧平举换成了这个训练日里已有的前平举），两个位置的第 1 组会写到同一条记录上，互相覆盖。

- 自定义方案编辑器已经禁止同一天选两次同一个动作
- **换动作没有禁止**：候选列表只排除了当前动作本身

修正：换动作的候选排除当天训练日已有的动作（5.4）。主键不改。

### 9.3 加重建议拿当前计划判断「做满」

见 5.5。新记录存 `targetReps` `targetSets` 后修正。

### 9.4 「上次成绩」口径不一致

`lastRecord` 取的是那天第一组，加重建议取的是最重一组。统一为最重一组。

### 9.5 示例数据的组号从 0 开始

`makeDemoSets` 生成的记录 id 里组号从 0 起，与真实记录的规则（从 1 起）不一致。目前只生成过去的日期，不会冲突；改为从 1 起，并给示例数据打上 `demo` 标记，示例数据永不上传。
