# 第一部分 · 设计方案

## 1. 目标与范围

动作库现在是静态文件 `app/data/exercises.js`（105 个，`g` 52 个健身房 / `h` 53 个居家），挡住三件事：动作详情页（插画 + 讲解，图片进不了代码包）、动作数量扩充、用户自建动作（没有存储和同步通道）。

**做法**：官方动作放服务端，同一套字段结构，用 `hot` 标热点；用户自建动作放服务端独立表，走 `/sync`；客户端优先读本地缓存。

| 做什么 | 不做什么 |
|---|---|
| 官方动作下发（含图片 URL、讲解） | 管理后台（用 `seed-catalog` 导 JSON） |
| 动作详情页 | 用户上传动作照片（要过 `imgSecCheck` + 配额） |
| 自定义动作：增删改选 | 搜索接口、分页（200 个本地过滤够用） |
| 换动作支持自建动作 | 视频 |

## 2. 数据模型

### 2.1 服务端三张表

**`exercises`（官方动作，全局内容，不进同步）**

```sql
create table if not exists exercises (
  id          text        primary key,              -- 'g1'，永不变、永不复用
  cn          text        not null,
  en          text        not null default '',
  part        text        not null,                 -- chest|shoulders|arms|back|legs|core
  place       text        not null default 'gym',    -- gym|home（只有两个值，见 §7.2）
  unit        text        not null default 'kg',     -- kg|bw|sec
  tips        text        not null default '',       -- ≤64 字，列表直接显示
  hot         boolean     not null default false,    -- 热点：只影响排序和内容制作顺序
  steps       jsonb       not null default '[]',     -- 分步讲解 string[]，≤10 步，可为空
  img_thumb   text        not null default '',       -- CDN URL，可为空
  img_detail  text        not null default '',       -- CDN URL，可为空
  retired     boolean     not null default false,
  updated_at  timestamptz not null                   -- 内容维护时间，仅供人看
);
create index if not exists exercises_hot_idx on exercises (hot) where hot;
```

没有 `rev` 列：清单版本由 `catalog_meta.rev`（整份）表达，详情缓存用 TTL，逐行版本和它的索引没有读写方。

**`catalog_meta`（整份版本号，客户端判断要不要重拉）**

```sql
create table if not exists catalog_meta (
  id         int         primary key default 1 check (id = 1),
  rev        bigint      not null default 1,
  updated_at timestamptz not null default now()
);
```

每次导入内容，同一个事务里 `rev = rev + 1`。不能用 `max(exercises.rev)`：下架也要让客户端知道，`max` 表达不了「整份变了」。

**`user_exercises`（用户自建动作，用户数据，跟 `sets` 一起同步）**

```sql
create table if not exists user_exercises (
  user_id    bigint      not null references users(id) on delete cascade,
  ex_id      text        not null,                 -- 'u-m8f2k9ab-a7x2'
  cn         text        not null,
  part       text        not null,
  place      text        not null default 'gym',
  unit       text        not null default 'kg',
  tips       text        not null default '',
  done       boolean     not null default true,    -- 墓碑
  updated_at timestamptz not null,                 -- LWW
  rev        bigint      not null,                 -- 拉取游标
  primary key (user_id, ex_id)
);
create index if not exists user_exercises_rev_idx on user_exercises (user_id, rev);
```

与 `sets` 同一套机制（自然主键 + rev + LWW + 墓碑），分页归并、坏行隔离、去回声全部复用现成代码。

### 2.2 客户端存储

| key | 内容 | 谁写 |
|---|---|---|
| `lj.catalog` | `{ rev, fetchedAt, list:[…] }`，官方动作列表字段（不含 `steps`/`imgDetail`）。正常路径读它 | `sync` 整份覆盖 |
| `lj.catalog.detail.{id}` | `{ steps, imgDetail, fetchedAt }`，LRU 保留 50 条，TTL 7 天 | 进详情页时写 |
| `lj.customEx` | 自建动作数组（含墓碑）：`{ exId, cn, part, unit, place, tips, done, updatedAt, rev }` | `db.js` 写、`sync` 应用下发 |
| `lj.sync.dirty` | 待上传队列，`x:` 前缀标记自建动作（`w:` 表示 workouts） | `db.js` / `sync` |
| `app/data/exercises.js` | 发版那天的官方清单快照，只在 `lj.catalog` 为空时用 | 发版 |

`lj.catalog` 丢弃等于「首装」——退回代码里那份，功能完整。`lj.customEx` 不能丢，但丢了能靠 `/sync` 拉回。

四条规则：

- **`lj.catalog.rev` 只在整份写入成功后更新**。从 `/sync` 拿到的 `catalogRev` 只用于当次比较，不落盘——写进 `lj.catalog.rev` 却没真正拉清单，会导致「rev 已前进、清单永远是旧的」。
- **详情缓存用 TTL 7 天**。`/api/catalog` 不返回逐行版本，没有比对依据，过期重拉一次即可。
- **「≤30」只计 `done=true` 的行**。墓碑由 `syncApply` 在应用下发时清掉；服务端墓碑不清（永久保留），量级按删除次数计，可忽略。
- **`resetAll()`（`db.js:1409`）要清**：`lj.catalog`、`lj.catalog.detail.*`（按前缀遍历 `wx.getStorageInfoSync` 的 keys 删除）、`lj.customEx`，外加队列里的 `x:` 待上传项。

### 2.3 字段规则

| 字段 | 规则 |
|---|---|
| `id` | 总长 ≤ 16 字节。官方 `^[a-z][a-z0-9]{0,5}$`；自建 `u-` + 8 位 base36 时间戳 + `-` + 4 位随机 = 15 字符（`36⁸ ≈ 2.8e12 > Date.now()`，base36 正好 8 位） |
| `cn` | 1–24 字 |
| `part` | 六选一，必填，服务端校验 |
| `unit` | `kg`/`bw`/`sec`，必填，服务端校验 |
| `place` | 只有 `gym`/`home` |
| `tips` | ≤64 字 |
| `steps` | `string[]`，≤10 步、每步 ≤200 字（不是 Markdown，见 §5） |
| `img_thumb`/`img_detail` | `https://` 开头，≤300 字节 |

示例 id：`u-m8f2k9ab-a7x2`。生成器必须保证 ≤16 并覆盖单测（见 §7.3）。

**id 加前缀的原因**：`ex_id` 会写进每一组记录、是主键的一部分永久存着，而它有两个生成者——官方（服务端建，能查重）和自建（手机上离线生成，没法查重）。纯数字自增必然撞：官方有 `1`，用户离线建也只能从 `1` 数；两台设备离线各建也都叫 `1`。前缀让两套 id 空间结构上不相交，所以不需要查重、不需要申请号段。`custom` 字段也能区分来源，但那是事后判断，前缀是生成时即保证不撞。

`g`/`h` 是既有习惯（按场所分组编号，`place` 已表达同样信息），继续往下排。已发出的 id 永不修改，也不在 id 里编码会变的东西。

## 3. 客户端行为

### 3.1 取动作列表

```js
var list = (lj.catalog.list.length ? lj.catalog.list : BUNDLE);  // 缓存优先，没拉过用代码里那份
return customExercises().concat(list);                           // 自建动作直接拼，无需去重
```

自建动作 id 以 `u-` 开头，与官方 id 结构上不相交。`lj.catalog` 和 `lj.customEx` 在 `app.onLaunch` 同步读进内存：下游 `initialWeight`（`plan.js:156`）、`todaySession`、`pickableExercises` 全是同步调用。

### 3.2 选动作面板

数据来自 `pickableExercises()`（`db.js:1296`），现在硬读 `EX.EXERCISES`（`db.js:1326`），改为读取上面的合并结果。

| 规则 | 理由 |
|---|---|
| 「我的动作」整组置顶 | 自建动作可挂在任意部位下，混进部位分组会找不到 |
| 部位分组内 `hot=true` 在前 | 最常选的那批滚动最少就能点到 |
| 部位分组**排除**自建动作 | 否则同一个动作在「我的动作」和部位分组里各出现一次 |
| 场所过滤跳过自建动作 | 显式 `if (e.custom) return true`，不靠 `place` 取巧 |

缩略图 `<image lazy-load>`，滚到才加载；`imgThumb` 为空显示统一占位块。

### 3.3 详情页

| 步骤 | 来源 | 耗时 |
|---|---|---|
| 1 渲染骨架（名字、部位、`tips`） | 已在内存的列表数据，同步 | 0 |
| 2 拉详情（`steps` + `imgDetail`） | 本地 `lj.catalog.detail.{id}` 命中且未过 7 天则用，否则 `GET /api/exercises/{id}`（要登录） | 一次请求 |
| 3 显示插画 | `<image src="{{imgDetail}}" lazy-load>` | CDN 决定 |

`steps` 是字符串数组，前端直接 `wx:for` 渲染。详情文本和插画都必须允许失败——失败就不显示，页面主体（名字、部位、`tips`）照常可用。

### 3.4 换动作

`alternatives(exId, planKey)`（`db.js:169`）现在被两处挡住：`EX.byId` 查不到自建动作（`db.js:170`）、`exercises.js:247` 的 `place` 等值比较。修法见阶段 E3。

## 4. 同步

### 4.1 官方动作清单

```
【读】启动同步读 lj.catalog → 立刻渲染；为空则用代码里那份顶上，同时触发一次全量拉

【追】搭在已有的 /sync 上：/sync 响应多一个 catalogRev
       catalogRev > 本地 rev        → GET /api/catalog?since=本地rev
       catalogRev < 本地 rev        → 按 0 处理，强制全量拉一次（自愈）
       200 → 整份写入（不是增量合并）+ 通知页面刷
       304 / 空 → 什么都不做
       失败 → 什么都不做，下次再试
```

**`?since=` 只决定「要不要给」**：响应永远是整份清单。`since >= 当前 rev` 返回 `304`，否则返回全量。客户端因此只有一条写入路径，不需要处理增量合并。

**自愈**：服务端库重置或回滚后，`catalogRev > 本地 rev` 永不成立，清单就再也不刷新。照 `store.go:445-448` 对游标的做法——本地 rev 大于服务端时按 0 处理。

**为什么搭 `/sync`**：`scheduleIdlePoll()`（`sync.js:256-260`）没有上传积压就直接 return，不存在空闲心跳。搭 `/sync` 后触发点就是现成的 `run()`：`onShow`、本地改动后防抖、失败重试，零额外请求。

代价两条：长时间停在前台又不记录时不刷新（另一台设备建的动作要等下次切前台或下次记录）；`/sync` 要登录，未登录用户永远停在代码里那份快照——记录功能本来就要登录，可接受。

**顺序由服务端定**：`order by hot desc, id`。Postgres 不带 `ORDER BY` 返回顺序未定义，两次拉取间顺序跳变会让用户觉得动作位置自己变了。要运营可调再加 `sort int` 列。

**`retired` 由客户端过滤**：接口返回整行（含 `retired=true`），整份替换才能覆盖本地旧的「未下架」状态；客户端在拼列表时过滤掉。

### 4.2 自建动作：`/sync` 的第 4 类资源

```
上传  db.saveCustomExercise() / removeCustomExercise()
        → 写本地 lj.customEx + 标脏（lj.sync.dirty 加一行，前缀 x:）
        → dirtyBatch 把 x: 的行放进 POST /api/sync 的 customExercises 数组
        → 服务端逐行 validateCustomExercise → 不合法进 rejected，合法 upsert（LWW，落败行刷 rev）

下载  pull 时 customExercises 与其他三类按 rev 归并下发 → 写回 lj.customEx → 通知页面

删除  done = false（墓碑），与 sets 一样跨设备传播
```

`x:` 行在 `dirtyBatch` 里优先入队：最多 30 行，否则积压 500 组记录的重度用户永远传不上动作。

配置文档（`user_config`）完全不动：`packConfig()` 不改、`CONFIG_VER` 仍是 1。自建动作不进它，因为需要服务端可校验、可查询、可按行合并、且改一条不该重传整份；设置类（profile / swaps / customPrograms）留在配置文档，它们确实是「每人一份、整份覆盖」的形状。

### 4.3 边界情况

| 场景 | 期望 |
|---|---|
| 首装、还没拉到过 | 用代码里那份顶上，选动作/记录/统计正常；拉到后整份替换 |
| 断网 / 服务端挂 | 照常用 `lj.catalog` 和 `lj.customEx`，不弹提示，下次同步追平 |
| 拉到新版本 | 整份替换 + 面板原地刷新；已选中在记录的动作不受影响 |
| 详情请求未登录 / 401 | 详情页只显示列表字段和 `tips`，不弹窗、不阻塞、不重试登录，拿不到大图就不显示 |
| 图片加载失败 | 不显示图，讲解和其余内容正常 |
| 官方动作 `retired` | 不再出现在可选动作里；历史记录照常显示（`sets.ex_cn` 冗余） |
| 删自建动作 | 墓碑跨设备传播；历史记录照常显示；换动作表里指向它的条目由读时校验兜底（§7.1） |
| 墓碑被更晚的编辑覆盖 | 走标准 LWW，动作复活。这是「删除后另一端离线改过」的必然结果，接受 |
| 两台设备各建动作、总量超过 30 | 都保留。上限只由客户端把关，服务端不强制，超出无害 |
| 先拉到 sets、后拉到动作 | 战报/记录页的名字取行里冗余的 `exCn`，显示正常；部位暂时为空，动作到达后恢复。不阻塞记录 |
| 自建动作行不合法 | 服务端拒该行、其余行照常入库；失败必须在界面上可见（§7.4） |
| 两台设备建同名动作 | 都保留（id 不同），不做自动合并 |
| 装回旧版小程序 | 不认识的字段忽略；`customExercises` 数组不认识也不影响 sets 同步 |

## 5. 接口

| 接口 | 鉴权 | 说明 |
|---|---|---|
| `GET /api/catalog?since=<rev>` | 免登录 | 只给 `imgThumb`（小图）。`{ rev, exercises:[id,cn,en,part,place,unit,tips,hot,imgThumb,retired] }`。响应永远是整份；`since >= 当前 rev` 返回 304；`order by hot desc, id` |
| `GET /api/exercises/{id}` | 要登录 | `{ id, steps, imgDetail }`。详细插画在这个接口后面，匿名面拿不到大图 |
| `POST /api/sync` | 要登录 | 请求和响应各加 `customExercises` 数组；响应加 `catalogRev`；计入 500 行上限 |
| `GET /healthz` `/readyz` | — | 不变 |

**详情格式是 `steps: string[]`，不用 Markdown**：省一个解析器、省包体、没有 XSS 面。内容侧按「一行一步」写，库里对应 `steps jsonb`。

**客户端需要一个带鉴权的 GET**：`sync.js` 只导出 `{ init, kick, stop, status, setTransport, ready }`（`:395-399`），`auth()`/`ensureToken()` 私有，`call()` 写死 `method: 'POST'`（`:133`）。因此 `sync.js` 增加 `request(path, opts)`：注入 token、遇 401 重登一次、失败抛错给调用方降级。`catalog.detail()` 用它，不自己拼 `wx.request`。

**`/api/catalog` 需要独立的 IP 限流器**：`ipLimit = newLimiter(1, 10)`（`main.go:51`）是给 `/api/login` 的。这个接口会被 `onShow` 频繁触发，复用会让正常用户撞限流，运营商 NAT 下整片 IP 更糟。单独建（建议 `newLimiter(2, 60)`）。

图片不经过 Go：`imgThumb`/`imgDetail` 直接是 CDN URL，服务端只负责存。内容进库用 `server/cmd/seed-catalog`（幂等 upsert by id，同事务 `catalog_meta.rev+1`）。

## 6. 数据源替换范围

`EX.byId`/`EX.EXERCISES`/`EX.alternatives` 全项目共 27 处，其中 9 处是 `EX.PART_CN[...]`（部位中文名映射，`db.js:326/1192/1319/1336/1484/1534/1657`、`builder/index.js:30/186`），不随数据源变。真正要换的是 **18 处**（`db.js` 13、`plan.js` 3、`pages/builder` 2）：

| 风险 | 位置 | 不改的后果 |
|---|---|---|
| 高 | `db.js:890` `saveSet` | 用自建动作记的每一条，`exCn` 存成 `u-…`、`part` 存成 `''`（`db.js:901-902` 的兜底链）→ 部位统计算不出来 |
| 高 | `db.js:1180` `makeBlock` | 记录页和战报（`todayWorkout` → `makeBlock`，`db.js:1248/1251`）的动作名显示 `u-…`、部位为空 |
| 高 | `db.js:554` `decorate` | 换动作指向自建动作被静默忽略 |
| 高 | `db.js:170` `alternatives` | 自建动作换动作列表恒为空 |
| 中 | `db.js:1093` `exercisePrefill` | 兜底 `{unit:'kg'}`，自建的计时/自重动作被预填成按 kg 记重量 |
| 中 | `db.js:323` `programSessions` | 方案中心「看看练什么」里名字显示 id、`part` 空 |
| 中 | `db.js:1326` `pickableExercises` | 选动作面板看不到自建动作 |
| 中 | `pages/builder/index.js:24/177` | 「我的方案」编辑器选不到自建动作 |
| 中 | `plan.js:87/156/199` | 方案生成解析不出自建动作（`199` 兜底归腿） |
| 低 | `db.js:996` `suggestWeight` | 有 `ex && ex.part === 'legs'` 保护（`db.js:1018`），不崩；只影响腿动作的加重档位 |
| 低 | `db.js:151/155` `exercises()`/`exerciseById()` 本体 | 本来就是被替换的目标 |

`todayWorkout`（`db.js:1212`）自身不查动作表，经 `makeBlock` 解析，所以改 `db.js:1180` 即可。`makeBlock` 的兜底改为优先用行里冗余的 `exCn`：`(rows[0] && rows[0].exCn) || exId`——计划里还没练的块 `rows` 为空，没有兜底来源，仍会退到 id（计划模板只引用包内 id，不触发）。

**唯一入口**：`utils/catalog.js` 持有合并数据源，`db.js`/`plan.js`/`pages/builder` 全部调它。不能在 `db.js` 里收一个内部 `find()` 让 `plan.js` 反向依赖 `db.js`——`db.js:16` 已 `require('../data/plan')`，反向依赖会让 `plan.js:87` 拿到尚未赋值的空 exports（`db.js:1678`），app 起不来。

## 7. 约束

### 7.1 `planSig()` 不含清单版本

`planSig()` 写进每一条组记录（`db.js:904`），轮转靠它过滤历史（`db.js:626-630` 的 `s.sig !== sig`），`db.js:57-62` 在签名变化时清空 `lj.swaps`。而 `catalog_meta.rev` 每次导入都 +1（改错字也算），把它加进签名等于每次内容更新都重置所有用户的 A/B/C 轮转。

风险改在读时兜住：`decorate()`（`db.js:554-557`）本来就有校验兜底，把三处 `EX.byId` 换成 `catalog.find()` 即可解析自建/下架/换动作，不需要签名机制。

顺带修兜底：`db.js:556` 和 `plan.js:199` 兜底成 `part: 'legs'`，把查不到的动作静默归到腿、污染部位统计。改成 `part: ''`，并在 `cn === id` 时界面显示「未知动作」。

### 7.2 `place` 只有 `gym`/`home`

现有筛选全是等值比较（`db.js:1327`、`builder/index.js:178`、`exercises.js:247`）。引入 `both` 后，该动作在「健身房」「居家」两个模式下都看不到（`'both' !== 'gym'` 也 `!== 'home'`），只在「全部」模式可见，等于永久隐身。要支持「两处都能做」就展开成两条记录。

自建动作同理：不能用 `place:'all'` 绕过筛选（同样被等值比较过滤掉），绕过场所过滤要显式写 `if (e.custom) return true`。

### 7.3 `id` 长度 ≤16

`validate.go:49` 卡的是 `len(r.ExID) > 16`。`ex_id` 是 `sets` 主键的一部分，超长会让**用这个动作记的每一组**被拒收，再按 §7.4 出队，数据静默丢失。生成器必须保证 ≤16 并覆盖单测。

### 7.4 被拒的行不能静默消失

`sync.js:220` 拿到 `rejected` 直接 `syncAck()`，从队列删掉、永不重试，只留 `console.warn`（`:217`）。`sets` 的字段可控，自建动作是用户输入，`part` 写错或 id 超长就会触发。

要求两条：被拒的动作在「我的动作」里标红并显示原因（行上存 `syncError`）；未同步条数在「我的 → 同步状态」可见。

### 7.5 不依赖「空闲就会轮询」

`scheduleIdlePoll()`（`sync.js:256-260`）没积压直接 return。任何依赖定时拉取的设计，先确认调度函数第一行没有 early return。

### 7.6 未知枚举必须在写库前归一

服务端能独立发版的前提是客户端对不认识的取值不崩：

| 未知值 | 客户端处理 |
|---|---|
| `part`（未来加的部位） | 显示用 `PART_CN[x] \|\| x`，可选中、可记录；**不进部位分布**——`partTerrain`/`partPct` 按 `TERRAIN_KEYS`（`db.js:1525` 六项写死）遍历，未知 part 进不了任何桶。统计页显示「未分类 N 组」，不让它静默消失 |
| `unit`（未来加的单位） | **写库前归一成 `kg`**，界面提示「按重量记录」。不能保留原值上传：`validate.go:53` 只认 `kg/bw/sec`，写别的会被拒收然后按 §7.4 丢组 |
| `place` | 不参与场所过滤，始终显示 |

原则：服务端校验是唯一真相，降级在写库之前完成，不把未知值送上去赌服务端宽容。

## 9. 数据量与成本

| 项 | 数值 |
|---|---|
| 单条动作文本 | ~160 字节（105 个 = 16 KB） |
| 官方 200 个动作列表字段 | ~32 KB，一次拉完 |
| 缩略图 / 插画 | ~15 KB / ~300 KB |
| 图片存储（200 个全配） | ~63 MB ≈ 0.008 元/月 |
| 流量①：缩略图 | 日活 1000 × 20 张 × 15 KB = 300 MB/天 ≈ 9 GB/月 |
| 流量②：插画 | 日活 1000 × 1 张 × 300 KB = 300 MB/天 ≈ 9 GB/月 |
| 合计 | ~18 GB/月 ≈ 4 元/月 |
| 单条自建动作 | ~130 字节，30 个 ≈ 4 KB（只计 `done=true`） |

贵的是插画本身：热点 30–60 张 = 0.3–1.8 万；200 个全做 = 2–6 万。所以结构上不区分，内容按 `hot` 分批：先画热点上线，其余先空着（图片字段允许为空，没图的动作照常能选能记录），看数据再决定补多少。
