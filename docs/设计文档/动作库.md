# 第一部分 · 设计方案

## 1. 目标

现在的动作库是纯静态文件 `app/data/exercises.js`（105 个，`g` 52 个健身房 / `h` 53 个居家），挡住三件事：动作详情页（插画 + 讲解，图片进不了代码包）、动作数量扩充、用户自建动作（没有存储和同步通道）。

**做法**：官方动作放服务端、同一套字段结构，用 `hot` 标热点；用户自建动作放服务端独立表、走 `/sync`。客户端优先读本地缓存。

| 做什么 | 不做什么 |
|---|---|
| 官方动作下发（含图片 URL、讲解） | ❌ 管理后台（用 `seed-catalog` 导 JSON） |
| 动作详情页 | ❌ 用户上传动作照片（要过 `imgSecCheck` + 配额） |
| 自定义动作：增删改选 | ❌ 搜索接口、分页（200 个本地过滤就够） |
| 换动作支持自建动作 | ❌ 视频 |
| | ❌ 把动作清单版本加进 `planSig()`（§6.1） |

## 2. 数据模型

### 2.1 服务端三张表

**`exercises`（官方动作，全局内容，不进同步）**

```sql
create table if not exists exercises (
  id          text        primary key,              -- 'g1'，永不变、永不复用
  cn          text        not null,
  en          text        not null default '',
  part        text        not null,                 -- chest|shoulders|arms|back|legs|core
  place       text        not null default 'gym',    -- gym|home（只有两个值，见 §2.3）
  unit        text        not null default 'kg',     -- kg|bw|sec
  tips        text        not null default '',       -- ≤64 字，列表直接显示
  hot         boolean     not null default false,    -- 热点：只影响排序和内容制作顺序
  detail_md   text        not null default '',       -- 存 JSON 数组（分步讲解 steps），可为空
  img_thumb   text        not null default '',       -- CDN URL，可为空
  img_detail  text        not null default '',       -- CDN URL，可为空
  retired     boolean     not null default false,
  updated_at  timestamptz not null,
  rev         bigint      not null
);
create index if not exists exercises_rev_idx on exercises (rev);
create index if not exists exercises_hot_idx on exercises (hot) where hot;
```

**`catalog_meta`（整份版本号，客户端靠它判断要不要重拉）**

```sql
create table if not exists catalog_meta (
  id         int         primary key default 1 check (id = 1),
  rev        bigint      not null default 1,
  updated_at timestamptz not null default now()
);
```

每次导入内容，同一个事务里 `rev = rev + 1`。不用 `max(exercises.rev)`——下架也要让客户端知道，`max` 表达不了「整份变了」。

**`user_exercises`（用户自建动作，用户数据，跟 `sets` 一起同步）**

```sql
create table if not exists user_exercises (
  user_id    bigint      not null references users(id) on delete cascade,
  ex_id      text        not null,                 -- 'u-m8f2k9a-a7x2'
  cn         text        not null,
  part       text        not null,
  place      text        not null default 'gym',
  unit       text        not null default 'kg',
  tips       text        not null default '',
  done       boolean     not null default true,    -- 墓碑
  updated_at timestamptz not null,                 -- LWW
  rev        bigint      not null,                 -- 拉取游标
  primary key (user_id, ex_id)
);
create index if not exists user_exercises_rev_idx on user_exercises (user_id, rev);
```

和 `sets` 完全同一套机制（自然主键 + rev + LWW + 墓碑），所以同步、分页归并、坏行隔离、去回声全部复用现成代码。

### 2.2 客户端存储

| key | 内容 | 谁写 |
|---|---|---|
| `lj.catalog` | `{ rev, fetchedAt, list:[…] }` 官方动作列表字段（不含详情）。**正常路径读它** | `sync` 整份覆盖 |
| `lj.catalog.detail.{id}` | `{ rev, detailMd, imgDetail }`，LRU 保留 50 条 | 进详情页时写 |
| `lj.customEx` | 自建动作数组（含墓碑），≤30 | `db.js` 写、`sync` 应用下发 |
| `lj.sync.dirty` | 待上传队列，新增 `x:` 前缀标记自建动作（已有 `w:` 表示 workouts） | `db.js` / `sync` |
| `app/data/exercises.js` | 发版那天的官方清单快照，只在 `lj.catalog` 为空时用 | 发版 |

`lj.catalog` 丢弃即等于「首装」——退回代码里那份，功能完整。`lj.customEx` 不能丢（用户数据），但丢了能靠 `/sync` 拉回。

两条补充规则：

- **详情缓存失效**：`lj.catalog.detail.{id}` 里存 `fetchedAt`，**TTL 7 天**。`/api/catalog` 不返回每行的 `rev`，所以没有逐行比对的依据——用 TTL 最简单，过期重拉一次即可。
- **「≤30」只计 `done=true`**；墓碑行由 `syncApply` 顺手清掉（没有定时任务，只能在应用下发时清）。

### 2.3 字段规则

| 字段 | 规则 |
|---|---|
| `id` | **总长 ≤ 16 字节**。官方 `^[a-z][a-z0-9]{0,5}$`；自建 `u-` + 8 位 base36 时间戳 + `-` + 4 位随机 = **15 字符**（`36⁸ ≈ 2.8e12 > Date.now()`，所以 base36 正好 8 位），留 1 位余量 |
| `cn` | 1–24 字 |
| `part` | 六选一，必填，服务端校验 |
| `unit` | `kg`/`bw`/`sec`，必填，服务端校验 |
| `place` | 只有 `gym`/`home`（§6.3 说明为什么） |
| `tips` | ≤64 字 |
| `steps` | `string[]`，≤10 步、每步 ≤200 字（**不是 Markdown**，见 §5） |
| `img_thumb`/`img_detail` | `https://` 开头，≤300 字节 |

未知 `part`/`unit` 的降级规则见 §6.7——这是「服务端能独立发版」的前提。

**id 有前缀的原因**：`ex_id` 会写进每一组记录、是主键的一部分永久存着，而它有两个生成者——官方（服务端建，能查重）和自建（**手机上离线生成，没法查重**）。纯数字自增必然撞：官方有 `1`，用户离线建也只能从 `1` 数；两台设备离线各建也都叫 `1`。前缀让两套 id 空间结构上不相交，所以不用查重、不用申请号段。

`custom` 字段也能区分官方/自建，但那是**事后判断**；前缀是**生成时就保证不撞**，两件事。

`g`/`h` 是既有习惯（按场所分组编号，`place` 字段已表达同样信息，属于冗余），继续往下排即可。**已发出的 id 永不修改，也不在 id 里编码会变的东西**。

示例：`u-m8f2k9ab-a7x2`（15 字符）。生成器里加一条 `assert(id.length <= 16)` 的单测——超过 16 会被 `validate.go:49` 拒收，且按 §6.4 该组记录会静默丢失。

## 3. 客户端怎么用

### 3.1 取动作列表

```js
var list = (lj.catalog.list.length ? lj.catalog.list : BUNDLE);  // 缓存优先，没拉过才用代码里那份
return customExercises().concat(list);                           // 自建动作直接拼，无需去重
```

自建动作 id 以 `u-` 开头，和官方 id 结构上不可能撞。`lj.catalog` 和 `lj.customEx` 在 `app.onLaunch` **同步**读进内存——下游 `initialWeight`（`plan.js:156`）、`todaySession`、`pickableExercises` 全是同步调用，不能变异步。

### 3.2 选动作面板

数据来自 `pickableExercises()`（`db.js:1296`），现在硬读 `EX.EXERCISES`（`db.js:1326`），改成上面的合并结果。显示顺序三条：

| 规则 | 理由 |
|---|---|
| 「我的动作」整组置顶 | 自建动作可能挂在任意部位下，混进部位分组会找不到 |
| 部位分组内 `hot=true` 在前 | 最常选的那批滚动最少就能点到 |
| 场所过滤**跳过**自建动作 | 显式 `if (e.custom) return true`，不靠 `place:'all'` 取巧（§6.3） |

缩略图 `<image lazy-load>`，滚到才加载；`imgThumb` 为空显示统一占位块。

### 3.3 详情页

| 步骤 | 来源 | 耗时 |
|---|---|---|
| 1 渲染骨架（名字、部位、`tips`） | 已在内存的列表数据，同步 | 0 |
| 2 拉详情（`steps` + `imgDetail`） | 本地 `lj.catalog.detail.{id}` 命中且未过 7 天则用，否则 `GET /api/exercises/{id}`（**要登录**） | 一次请求 |
| 3 显示插画 | `<image src="{{imgDetail}}" lazy-load>` | CDN 决定 |

`steps` 是字符串数组，前端直接 `wx:for` 渲染，**不解析 Markdown**。

详情文本和插画**都必须允许失败**——失败就不显示，页面主体照常可用。详情页不是关键路径。

### 3.4 换动作

`alternatives(exId, planKey)`（`db.js:169`）现在两处都挡住自建动作：`EX.byId` 查不到（`db.js:170`）、`exercises.js:247` 的 `place` 等值比较。见阶段 E3。

## 4. 同步

### 4.1 官方动作清单

```
【读】启动同步读 lj.catalog → 立刻渲染；为空则用代码里那份顶上，同时触发一次全量拉

【追】搭在已有的 /sync 上：/sync 响应多一个 catalogRev
      发现 catalogRev > 本地 rev → GET /api/catalog?since=本地rev
        200 → **整份写入**（不是增量合并）+ 通知页面刷（面板开着就重渲染）
        304 / 空 → 什么都不做
        失败 → 什么都不做，下次再试
```

**`?since=` 的语义定死为「要不要给」**：响应永远是**整份清单**，不做增量。`since >= 当前 rev` 时返回 `304 Not Modified`（或 `{rev, exercises:[]}`），否则返回全量。这样客户端只有一条写入路径（整份替换），不用处理「增量怎么合并」——200 条几十 KB，省这个复杂度不值得。

`catalogRev` 走 `/sync` 响应而不是另开轮询，因为 `scheduleIdlePoll()`（`sync.js:256-260`）**没有上传积压就直接 return，根本不存在心跳**。搭 `/sync` 后触发点就是现成的 `run()`：`onShow`、本地改动后防抖、失败重试。零额外请求。

代价：长时间停在前台又不记录时不刷新——另一台设备建的动作会在下次切前台或下次记录时出现。

**列表顺序由服务端定死**：`order by hot desc, id`。Postgres 不带 `ORDER BY` 返回顺序未定义，两次拉取之间顺序可能跳变（用户会觉得「动作位置自己变了」）。要运营可调再加 `sort int` 列。

**`retired` 由客户端过滤**：`/api/catalog` 会返回整行（含 `retired=true`），因为整份替换要能替换掉本地旧的「未下架」状态；**客户端在拼列表时过滤掉 `retired`**。这一点必须写明，否则容易出现「两边都没做，下架的动作一直显示」。

### 4.2 自建动作：`/sync` 的第 4 类资源

```
上传  db.saveCustomExercise() / removeCustomExercise()
        → 写本地 lj.customEx + 标脏（lj.sync.dirty 加一行，前缀 x:）
        → dirtyBatch 把 x: 的行放进 POST /api/sync 的 customExercises 数组
        → 服务端逐行 validateCustomExercise → 不合法进 rejected，合法 upsert（LWW，落败行刷 rev）

下载  pull 时 customExercises 和其他三类一起按 rev 归并下发 → 写回 lj.customEx → 通知页面

删除  done = false（墓碑），和 sets 一样跨设备传播
```

配置文档（`user_config`）**完全不动**：`packConfig()` 不改、`CONFIG_VER` 仍是 1。自建动作不进它，因为需要服务端可校验、可查询、可按行合并、且改一条不该重传整份。设置类（profile / swaps / customPrograms）继续留在配置文档——它们确实是「每人一份、整份覆盖」的形状。

### 4.3 边界

| 场景 | 期望 |
|---|---|
| 首装、还没拉到过 | 用代码里那份顶上，选动作/记录/统计正常；拉到后整份替换 |
| 断网 / 服务端挂 | 照常用 `lj.catalog` 和 `lj.customEx`，不弹提示，下次同步追平 |
| 拉到新版本 | 整份替换 + 面板原地刷新；**已选中在记录的动作不受影响** |
| 图片加载失败 | 不显示图，讲解和其余内容正常 |
| 官方动作 `retired` | 不出现在可选动作里；历史记录照常显示（`sets.ex_cn` 冗余） |
| 删自建动作 | 墓碑跨设备传播；历史记录照常显示；换动作表里指向它的条目由读时兜底处理（§6.1） |
| 自建动作行不合法 | 服务端拒该行、其余行照常入库；**失败必须让用户看得见**（§6.4） |
| 两台设备建同名动作 | 都保留（id 不同），不做自动合并 |
| 装回旧版小程序 | 不认识的字段忽略；`customExercises` 数组不认识也不影响 sets 同步 |

## 5. 后端接口

| 接口 | 鉴权 | 说明 |
|---|---|---|
| `GET /api/catalog?since=<rev>` | ❌ 免登录 | **只给 `imgThumb`**（小图），`{ rev, exercises:[id,cn,en,part,place,unit,tips,hot,imgThumb,retired] }`。响应永远是整份；`since >= 当前 rev` 返回 304。`order by hot desc, id` |
| `GET /api/exercises/{id}` | ✅ **要登录** | `{ id, steps, imgDetail, rev }`。详细插画在这个接口后面——这个接口要有用户身份，匿名面拿不到大图（§7） |
| `POST /api/sync` | ✅ | 请求和响应各加 `customExercises` 数组；响应加 `catalogRev`；计入 500 行上限 |
| `GET /healthz` `/readyz` | — | 不变 |

**`detail_md` 改成 `steps: string[]`（分步数组），不用 Markdown。** 理由：省一个解析器、省包体、没有 XSS 面。内容侧按「一行一步」写，前端直接 `wx:for` 渲染。

**`/api/catalog` 不能复用登录的 IP 限流器**：`ipLimit = newLimiter(1, 10)`（`main.go:51`）是给 `/api/login` 用的（1 r/s、burst 10）。`/api/catalog` 会被 `onShow` 频繁触发，直接复用会让正常用户撞限流，运营商 NAT 下整片 IP 更糟。**单独建一个**（建议 `newLimiter(2, 60)`）。

图片不经过 Go：`imgThumb`/`imgDetail` 直接是 CDN URL，服务端只存。内容进库用 `server/cmd/seed-catalog`（幂等 upsert by id，同事务 `catalog_meta.rev+1`）——**不写管理后台**，等出现「不会跑命令行的运营 / 一天改多次 / 需要非技术人员追溯」再建。

**E1 独立；E2 + E3 必须同批（E3 修的是 E2 换数据源后暴露的换动作 bug）；E4 独立。**

## 阶段 E1 · 服务端（约 1 天）

| 改动 | 位置 |
|---|---|
| 建三张表 | `schema.sql`（幂等建表，advisory lock 已有） |
| `GET /api/catalog`、`GET /api/exercises/{id}` | `handlers.go` + `main.go` 路由（catalog 用**新的** IP 限流器，见 §5） |

## 阶段 E2 · 客户端数据源与缓存（约 2 天）

**唯一数据源放在 `utils/catalog.js`，它不依赖 `db.js`。** 这是必须的：`db.js:16` 是 `const P = require('../data/plan')`，而 `plan.js` 只 `require('./exercises')` 和 `'../utils/date'`——如果反过来让 `plan.js` require `db.js`，CommonJS 会先拿到一个**还没赋值的空 exports**（`db.js` 的 `module.exports` 在 `:1678`），`plan.js:87` 一执行就 `db.exerciseById is not a function`，整个 app 起不来。

所以三处都依赖 `catalog.js`，形成单向依赖：

```
app/data/exercises.js（静态兜底）
        ↑
utils/catalog.js ── 读 lj.catalog / lj.customEx / exercises.js
  ├── list()            官方清单（已过滤 retired）
  ├── find(id)          官方 + 自建，返回带 custom 标记
  ├── custom()          自建动作（过滤墓碑）
  ├── alternatives(exId, planKey)
  └── detail(id)        详情（缓存优先，异步）
        ↑            ↑              ↑
      db.js       plan.js       pages/builder
```

| 改动 | 位置 |
|---|---|
| 新模块 `utils/catalog.js` | 上面的 `list/find/custom/alternatives/detail`；启动时同步读进内存；`catalogRev` 变化时整份替换并通知订阅者。**不 require `db.js`** |
| **被拒行的 kind 映射** | `storage.js:411-422` 的 `rejectedIds()` 现在只认 `set`/`workout`，**必须加 `customExercise` 分支**（按 `r.kind` + `r.index` 映射回 `x:` 队列 id）。不加的话 §6.4 的静默丢失照旧存在 |
| 自建动作队列 | `storage.js`：`dirtyBatch`（`:324`）加 `x:` 前缀并返回第三类；`applyRemoteExercises`（照 `applyRemoteWorkouts` 写）；**墓碑清理**：`syncApply` 里把 `done=false` 且 `rev` 已确认的行物理删掉（没有定时任务，只能顺手清）；`markAllDirty` 把 `lj.customEx` 排进队；`reset()` 清 `lj.customEx` 和 `x:` 队列项 |
| 同步接线 | `sync.js:196-203` 请求体加 `customExercises`；`:221` 应用下发；`:226` 存 `catalogRev` |
| 数据层替换 | `db.js` 的 13 处、`plan.js` 的 3 处、`pages/builder` 的 2 处改为调 `catalog.*`（**18 处**，另外 9 处是 `EX.PART_CN` 查中文名，不随数据源变，不用动） |
| 自建动作 CRUD | `db.js`：`saveCustomExercise` / `removeCustomExercise`（写 `lj.customEx` + 标脏 + 通知 `catalog`） |
| 页面 | `record` 选动作面板接新数据源；`my` 加「我的动作」入口；`builder/index.js:24/177` 能看到自建动作 |

**验收**：

- 首装断网能用代码里那份；拉到后断网用缓存零等待
- 两台设备建动作互相同步；删动作墓碑生效，且墓碑行被清掉
- 用自建动作记一组，`exCn`/`part` 正确（§6.2）
- `app/test.js` 补用例：id 格式与 ≤16、`x:` 队列进出、未知 `part`/`unit` 降级（§6.7）、自建动作记一组的 `exCn`/`part`
- `app/test-sync.js` 补用例：被拒的自建动作**不静默消失**（能拿到原因）

换动作的两道关卡都挡自建动作（§6.2 表格「高」风险三行），E2 换完数据源后这个 bug 会直接暴露成「换动作列表是空的」。

## 阶段 E4 · 动作详情页（约 0.5 天）

**不依赖插画**：图片字段本来就允许为空（§2.1），页面先上线，插画按 `hot` 单独排期。否则 0.3–1.8 万的外包周期会卡住一个 0.5 天的页面。

## 6. 禁令与陷阱

每条后面都是「不改会怎样」，来自对着代码核过的评审。

### 6.1 ❌ 不要把动作清单版本加进 `planSig()`

`planSig()` 被**写进每一条组记录**（`db.js:904`），轮转靠它过滤历史（`db.js:626-630` 的 `s.sig !== sig`），`db.js:57-62` 还会在签名变化时清空 `lj.swaps`。而 `catalog_meta.rev` 每次导入都 +1——改个错字也算。所以加进去等于：**每次内容更新都重置所有用户的 A/B/C 轮转**。

正确做法：不动 `planSig()`，把风险在读的时候兜住——`db.js:554-557` 的 `decorate()` 本来就有兜底，把那三处 `EX.byId` 换成 `catalog.find()` 就能解析自建/下架/换动作，不需要任何签名机制。

顺带修兜底 bug：`db.js:556` 和 `plan.js:199` 兜底成 `part: 'legs'`，把查不到的动作**静默归到腿**、污染部位统计。改成 `part: ''`，并在 `cn === id` 时界面标「未知动作」。

**验收**：随便改一次官方内容（改错字），轮转、A/B/C 顺序、历史训练日统计完全不变。

### 6.2 ❌ 别以为「只换数据源」只改几个方法

全项目直接调 `EX.byId`/`EX.EXERCISES`/`EX.alternatives` 共 **27 处**，但其中 **9 处是 `EX.PART_CN[...]`**（部位中文名映射，`db.js:326/1192/1319/1336/1484/1534/1657`、`builder/index.js:30/186`），**不随数据源变，不用动**。真正要换的是 **18 处**（`db.js` 13、`plan.js` 3、`pages/builder` 2）。按风险：

| 风险 | 位置 | 不改会怎样 |
|---|---|---|
| 高 | `db.js:890` `saveSet` | 用自建动作记的每一条，`exCn` 存成 `u-…`、`part` 存成 `''`（`db.js:901-902` 的兜底链）→ 部位统计直接算不出来 |
| 高 | `db.js:554` `decorate` | 换动作指向自建动作被静默忽略 |
| 高 | `db.js:170` `alternatives` | 自建动作换动作列表恒为空 |
| 中 | `db.js:323` **`programSessions`**（方案中心「看看练什么」） | 方案里出现自建动作时名字显示 id、`part` 空 |
| 中 | `db.js:1326` `pickableExercises` | 选动作面板看不到自建动作 |
| 中 | `pages/builder/index.js:24/177` | 「我的方案」编辑器选不到自建动作 |
| 中 | `plan.js:87/156/199` | 方案生成解析不出自建动作（`199` 兜底归腿） |
| 低 | `db.js:151/155`（`exercises()`/`exerciseById()` 本体）、`996`、`1093`、`1180` | 名称/单位显示不对，不影响数据 |

**`todayWorkout`（`db.js:1212`）不用改**——它按记录里冗余的 `exCn` 分组显示，不查动作表。

**做法**：唯一数据源在 `utils/catalog.js`（见 E2），`db.js`/`plan.js`/`pages/builder` 全部调它。**不要**在 `db.js` 里放 `findEx` 然后让 `plan.js` 反向依赖 `db.js`——那是循环依赖，app 起不来。

**验收**：用自建动作记一组，存下来的 `exCn` 是中文名、`part` 是真实部位。

### 6.3 ❌ 不要引入 `place: 'both'`

现有筛选全是等值比较（`db.js:1327`、`pages/builder/index.js:178`、`exercises.js:247`）。加 `both` 后，在「健身房」「居家」两个主模式下都看不到它（`'both' !== 'gym'` 也 `!== 'home'`），只在「全部」模式可见——**永久隐身**。要支持「两处都能做」就展开成两条记录。

同理，自建动作**不能**用 `place:'all'` 来绕过筛选（`'all'` 和 `gym`/`home` 都不等，一样被过滤掉）；绕过场所过滤要显式写 `if (e.custom) return true`。

**验收**：Profile 里切换场所，自建动作始终出现在「我的动作」组里。

### 6.4 ❌ 被拒绝的行不能静默消失

`sync.js:220` 拿到 `rejected` 直接 `syncAck()`，**从队列删掉、永不重试**，只有 `console.warn`（`sync.js:217`）。以前 sets 字段可控；现在自建动作是**用户输入**，`part` 写错或 id 超长会让**用它记的每一组**都被拒。

必须做两件事：① 被拒的动作在「我的动作」里标红并显示原因；② 未同步条数在「我的 → 同步状态」可见。

### 6.5 ❌ `id` 长度必须 ≤16

`validate.go:49` 卡的是 `len(r.ExID) > 16 → "exId 为空或过长"`。超长 → 组记录被拒 → 按 §6.4 静默出队 → 该组永久丢失。生成器必须保证 ≤16 并写进测试。

### 6.6 ❌ 别假设「空闲就会轮询」

`scheduleIdlePoll()`（`sync.js:256-260`）没积压直接 return。任何依赖「定时拉取」的设计都要先确认调度函数第一行没有 early return。本模块的做法见 §4.1。

### 6.7 ❌ 未来加枚举时必须有降级

服务端能独立发版的**前提**是客户端对不认识的取值不崩。规则：

| 未知值 | 降级为 |
|---|---|
| `part: 'glutes'`（未来加的部位） | 归入「其他」分组（`PART_CN[unknown]` 显示原始值），**动作不丢、不崩** |
| `unit: 'min'`（未来加的单位） | 按 `kg` 处理（记录时仍写原始 `unit`，只是加重建议按 kg 算） |
| `place` 未知 | 不参与场所过滤，始终显示 |

实现上就是 `PART_CN[x] || x`、`UNIT_SET.has(u) ? u : 'kg'`，并加进 `test.js` 用例。

## 7. 上线前检查

插画是最贵的资产（§8），必须做防抓：

| 项 | 做法 |
|---|---|
| **详细插画必须在登录后面** | `/api/catalog` **只返回 `imgThumb`**（小图），`imgDetail` 只从 `GET /api/exercises/{id}` 拿，而这个接口要求登录。Referer 白名单挡不住 `curl -H 'Referer: …'`，但挡得住匿名批量抓——**一行成本，把大图移出匿名面** |
| CDN 防盗链 | COS/OSS 的 Referer 白名单，放行 `https://servicewechat.com` |
| 图片压缩 | 上传前压 WebP：缩略 240px、插画 1080px |
| `downloadFile` 域名 | 若做「保存插画到相册」，要加到小程序后台的 downloadFile 域名。`<image src>` 通常不走 request 白名单，但 `downloadFile` 走——**上线前真机各验一次** |
| 域名与备案 | CDN 域名和 API 域名**一起备案**（P0 未开始，合并提交，别分两次多等 20 天） |
| 限流 | `/api/catalog` 免登录，**用单独的 IP 限流器**（别复用 `ipLimit`，见 §5） |

签名 URL（短有效期）是更强的方案，第一版不用。

## 8. 数据量与成本

| 项 | 数值 |
|---|---|
| 单条动作文本 | ~160 字节（105 个 = 16 KB） |
| 官方 200 个动作列表字段 | ~32 KB，一次拉完 |
| 缩略图 / 插画 | ~15 KB / ~300 KB |
| 图片存储（200 个全配） | ~63 MB ≈ 0.008 元/月 |
| 流量①：缩略图 | 日活 1000 × 20 张 × 15 KB = 300 MB/天 → **~9 GB/月** |
| 流量②：插画 | 日活 1000 × 1 张 × 300 KB = 300 MB/天 → **~9 GB/月** |
| 合计 | ~18 GB/月 ≈ **4 元/月** |
| 单条自建动作 | ~130 字节，30 个 ≈ 4 KB（「30」只计 `done=true`） |

**贵的是插画本身**：热点 30–60 张 = 0.3–1.8 万；200 个全做 = 2–6 万。所以**结构不区分、内容按 `hot` 分批**：先画热点上线，其余先空着（图片字段允许为空，没图的动作照常能选能记录），看数据再决定补多少。
