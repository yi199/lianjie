## 2. 关键路径（不是写代码）

```
买域名 → 提交 ICP 备案（1–20 工作日）
  → 小程序后台「开发管理 → 服务器域名 → request 合法域名」填 https://api.<域名>
  → 正式版可用
```

**备案只卡上线，不卡开发。** 开发期：

- 后端 `DEV_MODE=true`：登录不调微信，`code` 直接当用户标识
- 开发者工具「详情 → 本地设置 → 不校验合法域名」：可以直连 `http://localhost:8080`
- 真机预览开「调试模式」也不校验域名

所以备案和开发完全并行，第一天就提交即可。

> 免备案备选：腾讯云 CloudBase 云托管跑同一个 Docker 镜像，用它的默认域名。代价是付费 + 绑定腾讯云。

└──────────────────────────┬──────────────────────────┘
                           │ HTTPS  POST /api/sync（唯一写入口）
                    ┌──────▼──────┐
                    │   Nginx     │  TLS、limit_req、X-Real-IP
                    └──────┬──────┘
              ┌────────────┼────────────┐
         ┌────▼───┐   ┌────▼───┐   ┌────▼───┐
         │ api #1 │   │ api #2 │   │  …     │   无状态，可水平扩
         └────┬───┘   └────┬───┘   └────┬───┘

**为什么本地优先**：健身房常在地下室、信号差。「完成这组」这个动作任何情况下都不能等网络。同步是后台行为，失败只是晚一点上传，用户无感知。

## 4. 数据模型与同步协议

### 4.1 什么是真相

| 数据 | 性质 | 服务端存法 |
|---|---|---|
| 组记录 `sets` | 唯一业务真相，逐条产生 | 一行一组，自然主键 |
| 身体指标 `metrics` | 逐条产生 | 一行一个（种类, 日期） |
| 配置文档 | 设置 + 换动作 + 自定义方案 | 每用户一行 JSON，整份覆盖 |
| 训练日队列、战报、统计、PR、地形… | **派生量** | **不存**，客户端从上面三样现算 |

组记录主键 `(user_id, date, ex_id, set_no)` 来自客户端 `db.js` 的 `id = date-exId-setNo`。这个自然主键让**重复上传只会覆盖、永不产生重复行**——断网重传、超时重试、多端并发全部安全，同步逻辑因此可以「失败就整批重来」。

### 4.2 增量游标：为什么用版本号 `rev` 而不是时间

初版设计是「拉取 `updated_at > since` 的行」，其中 `updated_at` 是客户端写入时刻、`since` 是服务端时间。**两台机器的时钟混用，会静默丢数据：**

```
设备 A 已同步到 since = 10:00（服务端时间）
设备 B 时钟慢 5 分钟，在真实 10:02 写了一组 → updated_at = 09:57
设备 A 拉取 updated_at > 10:00 → 永远拉不到这一组，且没有任何报错
```

**现方案**：服务端每次写入时给这一行分配一个**按用户递增的版本号 `rev`**，拉取看 `rev > cursor`。`rev` 只由服务端产生，和任何时钟无关。

`updated_at`（客户端时刻）仍然保留，但**只用于冲突裁决**（§4.3），不用于拉取。

### 4.3 冲突裁决：LWW + 时钟夹紧 + 落败行回推

同一行被两台设备改过，**客户端时刻更新的赢**（Last-Write-Wins）。三个补丁让它在不可信时钟下仍然收敛：

1. **时钟夹紧**：客户端时刻比服务器快超过 2 分钟，按服务器时间记。否则一台时钟被调到明年的手机，它写的每条记录都会永远赢。
2. **落败行回推**：上传的行输了 LWW，服务端不报错，而是给服务端的赢家版本换一个新 `rev`，让它出现在本次的拉取结果里。这样上传方一定能拿到赢家，不会停在自己的旧值上。
3. **严格递增的本地时间戳**：同一毫秒内连改两次也拿到不同的 `updatedAt`，否则「上传途中又改了」判断不出来（§4.6）。

> 健身记录的冲突在现实中极少：同一组同时在两台设备上改的概率接近零。LWW 的价值在于**确定性**——任何情况下所有设备最终看到同一个值。

### 4.4 墓碑（取消勾选 / 删除）

**墓碑**就是「删除不真删，而是留一条标记 `done=false` 的记录」。

为什么同步系统里删除必须这样做：

```
手机 A 取消了一组，如果直接删掉 → 服务端看到的只是「A 那边没有这条」
  → 分不清是「被删了」还是「A 还没上传过」
  → 平板 B 上还有这一组，下次同步又把它传回来 → 删掉的组「复活」
```

留一条 `done=false`，相当于明确告诉所有设备「这组被取消了」。统计、战报、PR 全部只算 `done=true`，对用户来说和删除完全一样。

**墓碑不会无限堆积**：客户端上传成功后，本地就把这条墓碑物理删掉（服务端已经有了，本地不需要）。服务端保留墓碑，体积可忽略（一行约 100 字节）。

**同步未开启时**（纯本地模式）取消勾选直接物理删除，不留墓碑——没有别的设备需要通知。

> 这也修复了一个**现存 bug**：`pages/record/index.js` 的 `onToggle` 取消勾选时什么都不写，而 `db.saveSet()` 的 `done:true` 是写死的 → 页面显示未勾选，统计仍然算它。改造后取消勾选调用 `db.uncheckSet()`。

### 4.5 配置文档

设置（水平 / 频率 / 场所 / 当前方案 / 是否走完引导）、换动作表、自定义方案打包成一份 JSON，**整份 LWW**：

- 它们会**联动修改**：启用一个方案 = 改设置 + 换动作表清空（训练日编号含义变了）。分三个资源同步，两台设备交错修改时可能出现「设置是 A 设备的、换动作是 B 设备的」这种组合。
- 体积小（几 KB），整份传不心疼；冲突概率极低（设置一年改几次）。
- 服务端**不解析**它的内部结构，只校验「是 JSON 对象、不超过 64KB」。结构由客户端定义并带版本号 `v`，前端升级字段不需要改后端。

训练日队列（`lj.plans`）**不在配置文档里**，客户端拿到配置后用 `applyProgram()` 重新推导（D5）。

### 4.6 客户端的三条应用规则

| 时机 | 规则 | 防的是什么 |
|---|---|---|
| 上传成功后清队列 | 只清「发出去之后没再改过」的行（比对 `updatedAt`） | 上传途中用户又改了 → 新改动不能被当成已上传丢掉 |
| 应用下发的行 | 本地这行还在队列里（有未上传改动）→ 先不覆盖 | 用户刚改的值被服务端旧值冲掉。等它上传后由服务端裁决，赢家下次回来 |
| 应用下发的墓碑 | 本地直接物理删除 | |

### 4.7 首次接入（老用户的全量上传）

本地已有的全部真实记录在**第一次同步时整体进入上传队列**，分批（每批 500）传完。示例数据带 `demo` 标记，永不上传。

因为本地保留全量（§7），**不存在「先截断后上传会丢历史」的顺序风险**——原方案里最危险的一步消失了。

## 5. 一致性、并发与可用性

目标是「快速开发的前提下，具备够用的并发、可用和一致性」。下面写清楚**承诺什么、不承诺什么、靠什么实现**。

### 5.1 一致性承诺

| 承诺 | 实现方式 |
|---|---|
| **读己之写**：自己刚记的组立刻可见 | 页面只读本地，写本地是同步调用 |
| **不重**：同一组无论上传几次，服务端只有一行 | 自然主键 + `ON CONFLICT` upsert |
| **不漏**：一台设备按游标翻页，一定能拿到所有其他设备的写入 | `rev` 游标 + 同用户写入串行（§5.2）+ 快照读（§5.2） |
| **收敛**：所有设备最终看到同一个值 | LWW 确定性裁决 + 落败行回推（§4.3） |
| **单次同步原子**：一批上传要么全部生效要么全部不生效 | 一个事务；失败客户端整批重传（幂等，无副作用） |
| **删除可传播** | 墓碑（§4.4） |

**不承诺**：跨设备的强一致（A 设备记完，B 设备要等下一次同步才看到，通常在几秒到几十秒）。对健身记录这是合理的取舍。

### 5.2 并发模型

**服务端无状态**：会话靠 JWT，不存进程内存。任意多个 API 实例可以放在 Nginx 后面。

**不同用户完全并行**，**同一用户的写入串行**：

```sql
-- 每次上传的第一句：给这批行分配 n 个连续版本号，同时锁住该用户这一行直到提交
update users set rev = rev + $n where id = $uid returning rev;
```

为什么必须串行：如果两个事务并发分配了 rev 10 和 11，而 11 先提交，此时另一台设备来拉取，拿到 11 后游标前进到 11——之后 10 提交，就**永远被跳过了**。用户行锁保证「rev 小的一定先提交」。

代价是同一用户的并发上传排队。一个人同时在线的设备最多两三台，每次上传事务几毫秒，可以忽略。

**拉取用可重复读快照**：`users.rev` 和各表数据从同一个快照读出，「这一页已经拿全」的判断不会被并发写入打破。

**其他并发细节**：

| 项 | 做法 |
|---|---|
| 连接池 | pgxpool，单实例上限 20（`DB_MAX_CONNS`）。多实例时 实例数 × 上限 < Postgres `max_connections` |
| 多实例同时启动建表 | `pg_advisory_lock` 串行化，防并发 DDL |
| 批量写 | pgx Batch，一次网络往返写完 500 行 |

### 5.3 可用性

**第一道防线是本地优先**：后端整个挂掉，用户照常记录、照常看统计，只是暂时不能换设备。所以后端的可用性目标可以务实一些。

| 措施 | 作用 |
|---|---|
| 客户端指数退避重试（5s → 10s → … 封顶 5 分钟，带随机抖动） | 后端恢复时不会被所有客户端同时打爆 |
| 所有写入幂等 | 超时、断线、重复点击都可以放心重试 |
| 请求超时 10 秒（context 传到 SQL） | 一条慢查询不会占住连接池 |
| 按用户限流（每秒 2 次，突发 20） | 客户端出 bug 死循环时，不拖垮其他用户 |
| `/api/healthz`（进程存活）与 `/api/readyz`（数据库可达）分开 | 数据库抖动时摘流量，而不是把所有实例一起重启 |
| 优雅停机（10 秒排空） | 发版时不中断正在进行的同步 |
| 容器 `restart: unless-stopped` | 进程崩溃自动拉起 |
| 每日 `pg_dump` 备份，保留 14 天，异地存一份 | 数据库损坏可恢复 |

**目标值（单机阶段）**：

| 指标 | 目标 | 说明 |
|---|---|---|
| RPO（最多丢多少数据） | 服务端 ≤ 24 小时；**用户侧实际为 0** | 丢失的服务端数据会被各设备本地的全量历史重新上传补回 |
| RTO（多久恢复） | ≤ 1 小时 | 新机器 + 最近备份 + `docker compose up` |
| 可用性 | 99.5% | 单机够用；要更高时换托管 PostgreSQL（主备）+ 2 个 API 实例 |

> 本地保留全量的另一个好处：**服务端数据其实是「所有设备本地数据的并集」**。最坏情况下服务端全丢，各设备重新上传即可恢复。

### 5.4 容量

实测口径：一周 3 练、健身房、每次 4–5 个动作。

| 指标 | 数值 |
|---|---|
| 一周 | 47 组 ≈ 8 KB |
| 一年 | 2,444 组 ≈ 391 KB |
| 十年老用户的全量 | 约 2.4 万行，按 `(user_id, ex_id, date)` 索引聚合是亚毫秒级 |
| 1 万活跃用户的同步流量 | 每人每天约 5–10 次同步 → 约 1 次/秒，单实例远未到瓶颈 |

## 6. 为什么不做派生表 / 定时任务 / 缓存

判据不是「算得贵不贵」，而是**「输入数据在不在客户端手里」**。本地保留全量之后，所有统计的输入都在客户端，**全部由客户端现算**。

三个失败模式（保留原论证）：

1. **写入路径有多条**（勾选、改已勾选组、底部按钮推进），派生表要在每条路径上都维护，漏一条就漂。
2. **漂了之后无法自查**：明细 4 组、聚合表也 4 组，两边一致但都是错的。现算方案里只有一份真相，不一致在结构上不可能发生。
3. **定时任务引入时间边界 bug**：23:59 练完、00:00 任务才跑 → 战报显示 0 组。

产品层面：健身 app 的核心爽点是「练完一组，数字立刻变」，任何延迟一致都直接毁掉这个时刻。

`GET /api/history/summary`（全量聚合）保留为**可选接口**：新设备还没拉完历史时先显示总览、以及运营排查用。它是实时查询，不落表。

## 7. 本地存储：按月分 key

```
lj.sets.months    ['2026-09', '2026-10']   有数据的月份
lj.sets.2026-10   [row, …]                 这个月的组记录（含待上传的墓碑）
lj.sync.dirty     { rowId: updatedAt }     待上传队列
lj.sync.cursor    1234                     拉取游标
lj.config.meta    { updatedAt, dirty }     配置文档的版本与是否待上传
lj.auth           { token, expiresAt }
```

| | 单 key 存全部（现状） | 按月分 key |
|---|---|---|
| 容量上限 | 单 key 1MB → 约 31 个月写满 | 总量 10MB → 二十多年 |
| 每存一组要重写 | 全部历史 | 当月约 33KB |
| 历史完整性 | — | 全量在本地，PR / 连续天数 / 加重建议都不受影响 |

`storage.js` 在内存里缓存已读的月份，所有写入都经过它，缓存不会和存储不一致。老版本的 `lj.sets` 在第一次读取时自动迁移成分月格式（先写新 key、最后删老 key，中途崩溃下次还能重来）。

## 8. 安全

| 项 | 做法 |
|---|---|
| 身份 | 一律从 JWT 取 `uid`，**永远不接受前端传 userId** |
| `session_key` | 不返回前端、不入库 |
| 生产配置兜底 | 非 `DEV_MODE` 时，JWT 密钥是默认值或短于 32 字节、或缺微信凭证 → **拒绝启动** |
| `DEV_MODE` | Compose 默认关闭，只在本地 `.env` 里打开 |
| 输入校验 | 每行校验日期、单位、数值范围、文本长度；坏行逐条拒收，不影响同批好行 |
| 请求体 | 上限 2MB；单次上传上限 500 行 |
| 传输 | 仅 HTTPS（Nginx 终止 TLS） |
| 隐私 | 体重等身体数据属于个人信息：上线前配置「用户隐私保护指引」，提供数据导出与注销 |

## 9. 明确不做的事

| 不做 | 为什么 |
|---|---|
