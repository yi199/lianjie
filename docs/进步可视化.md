# 练界 · 进步可视化设计思路 v0.1（业务向）

> 本文回答「**用户怎么看见自己变强了**」：要衡量什么、依据什么理论、需要哪些数据、分几步做。
> **不涉及前端展现形式和视觉风格**，那部分另开专题讨论。本文刻意只定义「数据和事件」，不定义「图表长什么样」，给视觉设计留出全部空间。
> 架构与接口见 [`技术方案.md`](./技术方案.md)、[`后端接口契约.md`](./后端接口契约.md)，排期见 [`开发计划.md`](./开发计划.md)。

## 1. 为什么要做

### 1.1 现状：我们只记录了「勤奋」

现在的数据页和战报回答的都是「练了多少」：

| 现有指标 | 回答的问题 |
|---|---|
| 本月训练天数、本周 2/3 | 我来了几次 |
| 组数、吨数、近 12 周训练量 | 我练了多少 |
| 部位分布、动作 TOP5 | 我练了什么 |
| 今日 PR | 今天有没有破纪录（只有这一下） |

它们衡量的是**投入**，不是**结果**。

### 1.2 真正让人坚持下去的是「变强」

健身者最在意、也最容易放弃的原因，都和一件事有关：**我到底有没有在进步？**

- 「三个月前卧推 40kg，现在 60kg」——这句话比任何吨数都打动人
- 练了两个月体重没变、镜子里没变化，但**力量在涨**——这是坚持下去的最强理由
- 卡在一个重量好几周——用户需要知道「这正常吗？我该怎么办？」

**进步可视化是练界区别于「训练记事本」的核心功能。**

### 1.3 目标

| # | 目标 | 衡量方式（上线后） |
|---|---|---|
| G1 | 每个动作都能看到「从第一次到现在」的变化 | 练过 3 次以上的动作 100% 有进步数据 |
| G2 | 有一个入口一眼看到「我整体变强了多少、强在哪」 | 进入「整体变化」的周活跃比例 |
| G3 | 停滞时能被识别，并在健身规划上线后给出建议 | 停滞识别的准确度（用户反馈「说得对」的比例） |
| G4 | 让「变强」这件事被讲出来、被分享 | 高光时刻的分享率 |

## 2. 用户与场景

| 用户 | 典型状态 | 他最想看到的 |
|---|---|---|
| **新手**（练了 0–3 个月） | 进步快，每次都能加重或加次数 | 「比第一次强了多少」——强烈的正反馈 |
| **练过一阵**（3 个月–1 年） | 进步变慢，开始遇到平台期 | 「我还在进步吗？」「卡住了怎么办」 |
| **一直在练**（1 年以上） | 一个月涨 1% 都算好 | 长周期趋势、阶段对比、力量水平 |
| **居家训练者** | 没有杠铃，靠自重和变式 | 「从跪姿俯卧撑到标准俯卧撑」也是进步 |

### 关键场景

| 场景 | 时机 | 用户的问题 | 需要的数据 |
|---|---|---|---|
| S1 组间休息 | 刚做完一组，有 90 秒 | 我这个动作最近怎么样 | 单动作近期序列、和第一次的对比 |
| S2 训练结束 | 战报 | 今天有什么值得骄傲的 | 今天的新纪录、里程碑 |
| S3 周末回顾 | 打开 App 随便看看 | 我整体变强了吗 | 全身进步指数、各肌群、高光时刻 |
| S4 单动作深挖 | 想看某个动作的完整历史 | 这个动作是怎么一路练上来的 | 单动作全量序列、最好成绩、停滞区间 |
| S5 卡住了 | 连续几次没进步 | 这正常吗，我该怎么办 | 停滞识别 + 健身规划给的建议 |

**S3 是本功能最核心的入口**：用户不需要先选动作，打开就能看到整体变化（见 §7）。S4 的动作详情页是从整体入口点进去的下一层。

## 3. 核心概念

| 概念 | 定义 | 例子 |
|---|---|---|
| **实际负荷** | 这一组身体实际承受的重量，统一了负重和自重 | 卧推 60kg → 60；体重 70kg 的人做引体 → 70 |
| **进步模型** | 这个动作用什么方式衡量进步 | 卧推看估算极限，侧平举看次数，平板看时长 |
| **力量值** | 某次训练里，这个动作的表现，用模型自己的单位 | 估算极限 75kg / 12 次 / 90 秒 / 第 3 级 |
| **相对进步指数** | 力量值 ÷ 起点，没有单位，可以跨动作比较 | 1.32 = 比刚开始强 32% |
| **训练次（exposure）** | 「第几次练这个动作」，进步按次计，不按日历 | 卧推第 16 次 |
| **高光时刻** | 从数据里找出的、值得讲出来的事件 | 新纪录、第一次卧推 60kg、俯卧撑升级 |
| **停滞** | 一段时间内力量值没有超出正常波动的进步 | 卧推连续 4 次停在 50kg 做不满 |

## 4. 统一的动作模型

### 4.1 问题

不同动作的「变强」长得完全不一样：

- 卧推：重量涨了
- 引体向上：次数涨了，或者开始挂重量了；**它的负荷是体重本身**
- 卧推**没有**体重成分，不能拿体重去推导
- 平板支撑：时间变长了
- 居家俯卧撑：从跪姿换成了标准姿势——次数反而变少了，但这是进步

需要一套**所有动作都适用的统一描述**，而不是给每类动作写一套特殊逻辑。

### 4.2 第一层：实际负荷公式

每个动作都用同一个公式算出这一组的实际负荷：

```
实际负荷 = 体重 × 体重系数 + 外加重量 − 助力
```

| 动作 | 体重系数 | 外加重量 | 助力 | 体重 70kg 时的实际负荷 |
|---|---|---|---|---|
| 卧推 | **0** | 60 | — | 60 |
| 引体向上 | 约 1.0 | — | — | 70 |
| 负重引体 | 约 1.0 | 10 | — | 80 |
| 弹力带辅助引体 | 约 1.0 | — | 约 20 | 50 |
| 标准俯卧撑 | 约 0.64 | — | — | 45 |
| 跪姿俯卧撑 | 约 0.49 | — | — | 34 |

- **卧推这类负重动作的体重系数是 0**，公式自动退化成「外加重量」，和现在完全一样
- 俯卧撑的系数来自测力台研究（Ebben 等，2011）；**其他自重动作的系数需要专业校准**（见 §11）
- **用户没记录体重时**：自重动作无法算实际负荷，自动退回「看次数」，不影响使用

### 4.3 第二层：进步模型

实际负荷算出来之后，「怎么从一次训练里得出一个力量值」因动作而异。每个动作指定一种模型：

| 模型 | 适用 | 力量值 | 为什么 |
|---|---|---|---|
| **估算极限**（e1RM） | 复合动作：卧推、深蹲、硬拉、划船、推举、负重引体 | 当天最好那组的估算 1RM | 重量和次数都在变，需要折算到同一把尺子 |
| **次数**（reps） | 孤立动作（侧平举、弯举）、器械，以及常做高次数的动作 | 相同负荷下单组最多次数 | 估算公式在这些动作上不准（§5.1） |
| **时长**（duration） | 平板支撑、靠墙静蹲等静力动作 | 单次最长秒数 | |
| **进阶阶梯**（ladder） | 居家自重动作家族：俯卧撑、深蹲、引体等 | 当前到达的级别 + 该级别的次数 | 换更难的变式是自重训练的主要进步方式 |

**进阶阶梯举例**（具体级别待校准）：

```
俯卧撑家族：  墙上俯卧撑 → 跪姿 → 上斜 → 标准 → 下斜 → 窄距 → 单臂辅助
深蹲家族：    椅子辅助蹲 → 徒手深蹲 → 分腿蹲 → 保加利亚分腿蹲 → 单腿蹲
```

升一级，次数从 15 掉到 6，在阶梯模型里是**进步**，并会产生一个「升级」高光时刻。

### 4.4 第三层：统一输出

不管用哪种模型，每次训练都输出同样的结构：

| 字段 | 含义 |
|---|---|
| 力量值 | 模型自己单位的数（kg / 次 / 秒 / 级） |
| **相对进步指数** | 力量值 ÷ 起点（前 3 次训练的中位数），**没有单位** |
| 可信度 | 高 / 中 / 低（次数过高、缺体重、只做了 1 组等会降低） |
| 最好的一组 | 力量值来自哪一组，方便展示「60kg × 8」这样的实际成绩 |

**相对进步指数是整个功能的「通用货币」**：卧推 1.32、引体 1.50、平板 2.00，单位不同，但「比刚开始强多少」可以放在一起比、可以加权汇总成全身指数。

### 4.5 每个动作需要的属性

在现有动作库（105 个动作）上补充：

| 属性 | 说明 |
|---|---|
| 体重系数 | 0 = 纯负重；自重动作填系数 |
| 是否按单只记重量 | 哑铃动作（现在已经按单只记） |
| 进步模型 | 估算极限 / 次数 / 时长 / 进阶阶梯 |
| 可信次数上限 | 估算极限模型下，超过这个次数的组不参与估算（默认 10） |
| 进阶家族与级别 | 阶梯模型用 |
| 肌群参与度 | 主动肌与协同肌的权重，例：卧推 = 胸 1.0、三头 0.5、前束 0.3 |

肌群参与度替代现在每个动作只有一个「部位」的做法：卧推不只练胸，三头也在出力。这让「各肌群进步」的汇总更真实。

## 5. 力量值的理论依据

### 5.1 估算 1RM

1RM（one-rep max）= 只能完成一次的最大重量，是力量训练最通用的力量指标。实际测 1RM 有受伤风险，所以用「重量 + 次数」估算。

**公式**：采用 Epley 公式

```
估算 1RM = 重量 × (1 + 次数 ÷ 30)
```

| 依据 | 结论 | 对设计的影响 |
|---|---|---|
| LeSuer 等，1997（比较 7 个公式，卧推 / 深蹲 / 硬拉） | 次数越少越准，10 次以内误差小，超过 10 次误差明显变大 | 只用 10 次以内的组估算 |
| Reynolds 等，2006 | 建议用较少次数（约 10 次内）的组预测 1RM | 同上 |
| Hoeger 等，1990 | 相同 %1RM 下能做的次数因动作差异很大（器械腿举远多于卧推） | 孤立 / 器械动作改用「次数」模型 |
| 10 次附近 Epley 与 Brzycki 结果几乎一致 | 公式选择对结果影响很小 | 选最常用的 Epley 即可 |

### 5.2 没练到力竭的组：RIR 修正

公式默认这一组做到了极限。实际上大部分组还留有余力。

依据「还能再做几次」（RIR，Reps in Reserve）的研究（Zourdos 等，2016；Helms 等，2016），修正为：

```
估算 1RM = 重量 × (1 + (次数 + 剩余次数) ÷ 30)
```

**产品决定（已确认）**：剩余次数**可选录入，默认不录**。

- 录入方式只用三档：**轻松**（约 3 次）/ **刚好**（约 1 次）/ **力竭**（0）
- 不录时按「刚好」处理
- 为什么不录也有效：同一个人的用力习惯基本稳定，估算值的偏差是一致的，**看趋势不受影响**。我们需要的是趋势，不是精确的绝对值

### 5.3 当天取哪一组

取当天估算值最高、且次数在可信上限内的那一组。热身组重量轻，自然被排除，**不需要用户标记热身组**。

### 5.4 对用户的呈现原则

- **估算 1RM 是内部计算用的**，用于趋势、汇总和停滞识别
- 界面上展示**实际举起的成绩**（「60kg × 8」）和**相对变化**（「比第一次 +50%」）
- 不直接告诉新手「你的极限是 75kg」——避免有人去试极限重量受伤
- 例外：力量水平评级（§8）可以展示估算值，因为它面向的是主动填写了资料、想了解自己水平的用户

### 5.5 噪声：涨多少才算真进步

人每天的状态都有波动，涨 1% 可能只是睡得好。需要一个「最小有意义变化」阈值。

- 这个阈值没有统一定论，而且和训练年限强相关：新手一次涨 5%，老手一个月涨 1%
- **数据层不写死阈值，由健身规划按用户水平传入**；健身规划上线前先用一个保守的默认值（暂定 2.5%，待校准）

## 6. 停滞：数据层只给事实，判断交给健身规划

### 6.1 为什么不能简单地「连续 N 周没涨就算停滞」

- 「练三休一」和「练四休一」的人，同一个动作一周可能练 2 次也可能练 1 次——按日历算不公平
- 计划内的减载周力量本来就会下降，不能报成停滞
- 出差两周回来力量下降，是「中断」不是「停滞」
- 「该不该加重」取决于训练阶段：新手每次都该加，老手按阶段加

### 6.2 相关理论（供健身规划设计时深入）

| 理论 | 要点 | 对停滞判断的意义 |
|---|---|---|
| 刺激—恢复—适应（SRA）；体能—疲劳模型（Banister，1975） | 训练先产生疲劳，恢复后才体现为进步 | 两次训练的间隔决定能否看到进步 |
| 训练后肌肉蛋白合成升高约持续 24–48 小时（MacDougall 等，1995；Phillips 等，1997） | 同一部位合理间隔在 2–3 天量级 | 间隔过短 → 疲劳未恢复，不算停滞 |
| 每部位每周 2 次优于 1 次（Schoenfeld 等，2016）；总量相同时差异变小（2019） | 频率和总量要一起看 | 判断要结合训练量 |
| 每周训练量与肌肥大呈剂量关系（Schoenfeld 等，2017） | 每周组数是规划核心变量 | |
| 减载常见做法：每 4–8 周一次，约一周（Bell 等，2023 专家共识） | 减载期下降是计划内的 | 减载期的训练不参与停滞判断 |
| 进阶模型：新手每次加 → 中级每周加 → 高级按阶段（Kraemer & Ratamess，2004，ACSM） | 加重节奏取决于阶段 | 停滞的定义随水平变化 |

### 6.3 两层分工

| 数据层（本功能，现在做） | 健身规划层（以后做） |
|---|---|
| 按「第几次练这个动作」排列每次训练 | 定义训练节奏：三练一休 / 四练一休 / 自定义 |
| 每次训练的力量值、距上次间隔几天 | 定义阶段：积累期 / 强化期 / 减载期 |
| 这次训练是否落在减载期（按规划的日期推出） | 给出参数：噪声阈值、几次算停滞、间隔多久算中断 |
| 距最好成绩已经过了几次训练 | **判断状态**：进步中 / 停滞 / 疲劳 / 中断 |
| 趋势斜率（按次、按周两种） | **给出建议**：加重 / 保持 / 减重重来 / 换方案 |

健身规划上线前，数据层用一套保守的默认参数先做「停滞提示」，只陈述事实（「卧推已经 4 次没有超过 50kg × 10」），不给训练建议。

### 6.4 停滞的几种情况（规划层的判断参考）

| 情况 | 数据特征 | 可能的原因 | 建议方向（规划层给） |
|---|---|---|---|
| 该加了 | 重量多次不变，但每次都做满 | 用户没听系统的加重建议 | 鼓励加重 |
| 真停滞 | 重量多次不变，且做不满 | 平台期 | 减重重来、换次数方案、换变式 |
| 疲劳 | 多个动作同时下降，间隔偏短 | 恢复不足 | 安排减载 |
| 中断回落 | 间隔明显变长后下降 | 停练 | 降低重量找回状态 |

## 7. 整体变化：一个直接的入口

### 7.1 要回答的问题

用户打开就能看到，不需要先选动作：

1. **我整体变强了多少？** —— 全身进步指数
2. **强在哪、弱在哪？** —— 各肌群的进步
3. **哪些动作在涨、哪些卡住了？** —— 动作列表与状态
4. **这段时间有什么值得骄傲的？** —— 高光时刻

### 7.2 全身进步指数

```
全身指数 = Σ（各动作的相对进步指数 × 该动作的权重）
权重 = 该动作在这段时间的训练量占比 × 肌群参与度
```

- 练得多的动作影响大，偶尔做一次的动作不会把结果带偏
- 按周输出一个序列，可以看到「整体变强」的走势

### 7.3 各肌群进步

用每个动作的肌群参与度，把动作的进步分摊到肌群上。例：卧推进步 30%，按「胸 1.0、三头 0.5、前束 0.3」分摊。

这比现在的「部位分布」（练了多少组）多了一层意思：**不只是练了哪里，而是哪里变强了**。

### 7.4 高光时刻（最能打动人的部分）

从训练数据里自动找出值得讲的事件：

| 类型 | 触发条件 | 例子 |
|---|---|---|
| 新纪录 | 力量值超过历史最好 | 卧推新高 62.5kg × 8 |
| 整数关口 | 实际成绩首次跨过一个有象征意义的数 | 第一次卧推 60kg；第一次做满 10 个引体；平板首次撑满 2 分钟 |
| 升级 | 进阶阶梯升到新级别 | 俯卧撑：跪姿 → 标准 |
| 最大进步 | 一段时间内进步幅度最大的动作 | 这个月深蹲涨得最多：+15% |
| 突破停滞 | 停滞之后首次创新高 | 卧推卡了 5 次之后突破 |
| 第一次 | 第一次做某个动作（只记录，不算纪录） | 第一次做硬拉 |
| 坚持 | 某动作累计训练次数达到里程碑 | 卧推第 50 次 |

- 每种事件都带着「之前是多少、现在是多少、隔了多久」，前端可以据此讲故事
- **示例数据要能产生这些事件**（含一段停滞和一次突破），让新用户第一眼就看懂这个功能

### 7.5 与动作详情页的关系

```
整体变化（第一层，直接入口）
  ├── 全身指数与走势
  ├── 各肌群
  ├── 高光时刻 ──────────┐
  └── 动作列表 ──────────┤ 点击
                         ▼
               动作详情（第二层）
                 完整序列、最好成绩、停滞区间、每次训练的明细
```

入口放在哪（数据页、首页、战报之后）、长什么样，属于前端专题。

## 8. 力量水平评级（可选）

**产品决定（已确认）**：收集性别和体重，用于评级。

### 8.1 是什么

用「估算 1RM ÷ 体重」对照力量标准表，给出水平评级：新手 → 入门 → 中级 → 进阶 → 精英。

它回答的是新的问题：**不只是「我比过去强」，还有「我在同类人里处于什么水平」**。

### 8.2 注意事项

| 问题 | 处理 |
|---|---|
| 常见的力量标准表多数来自网络数据，不是同行评审研究 | 界面注明「仅供参考」；后期由专业体系替换数据源 |
| 只适用于少数标准动作（卧推、深蹲、硬拉、推举、引体） | 只对这些动作评级 |
| 性别、体重是个人信息 | 用户主动填写；可随时修改和清除；隐私协议写明用途 |
| 不填 | 评级功能不显示，其他功能完全不受影响 |

### 8.3 体重的双重用途

体重一份数据，三个地方用：

1. 自重动作的实际负荷（§4.2）
2. 力量水平评级（§8.1）
3. 身体指标的体重趋势（开发计划 P5）

体重按日期存为时间序列，算某次训练的实际负荷时，取**那天之前最近一次**记录的体重，而不是当前体重——否则减重后，过去引体的负荷会被「改写」。

## 9. 数据需求

### 9.1 原则：不改变已定的架构

- 所有进步指标都是**组记录的纯函数**，在手机上现算，**不建表、不落库**
- 好处：以后改公式、调系数，所有历史曲线**自动按新口径重算**，不需要数据迁移
- 本地保留全量历史（技术方案 D4）正是这个功能能离线运行的前提

### 9.2 需要新增的数据

| 数据 | 存在哪 | 必填 | 用途 |
|---|---|---|---|
| 剩余次数（RIR） | 组记录，新增可选字段 | 否，默认不录 | 估算 1RM 修正（§5.2） |
| 助力重量 | 组记录，新增可选字段 | 否 | 辅助引体等（§4.2） |
| 体重 | 身体指标（已有 `metrics` 表，kind = weight） | 否 | 自重负荷、评级 |
| 性别、出生年份 | 配置文档 | 否 | 力量水平评级 |
| 训练阶段（减载期等） | 配置文档（健身规划上线后） | 否 | 停滞判断排除减载期 |
| 动作属性（§4.5） | 动作库（小程序包内静态数据） | — | 统一模型 |

服务端改动很小：组记录表加两个可空列、同步接口透传。配置文档本来就不解析内容，不需要改。

### 9.3 对外提供的数据（给前端）

| 数据 | 内容 | 服务的场景 |
|---|---|---|
| 单动作序列 | 每次训练：第几次、日期、间隔、力量值、进步指数、最好的一组、可信度、所处阶段 | S1、S4 |
| 单动作趋势 | 起点、当前、最好、最好的日期、进步指数、趋势斜率、距最好已过几次 | S1、S4、S5 |
| 停滞识别 | 是否停滞、从哪次开始、持续几次、原因（参数由规划层给） | S5 |
| 整体变化 | 全身指数及按周序列、各肌群进步、动作列表与状态、高光时刻 | S3 |
| 今日高光 | 今天产生的高光时刻 | S2 |
| 力量水平 | 各标准动作的评级与估算值（用户填了资料才有） | S3、S4 |

数据结构的技术细节写入接口契约（客户端内部接口部分），实现时定稿。

## 10. 数据质量

进步曲线对异常值非常敏感，一个手误就能毁掉整条线、误报新纪录。

| 问题 | 处理 |
|---|---|
| 手误输入（50 输成 500） | 输入重量超过该动作历史最好的 1.5 倍时，录入当场确认 |
| 次数过高（30 次的组） | 超过可信上限，不参与估算 1RM，降低可信度 |
| 数据太少 | 练过不到 3 次的动作不出趋势，用「再练 2 次就能看到你的变化」代替 |
| 换了动作（通过「换一个」） | 每个动作独立计算；同一进阶家族的动作在阶梯模型下合并 |
| 哑铃按单只记重量 | 同一动作内口径一致，不影响趋势；不做跨动作的绝对值比较 |
| 示例数据 | 不参与真实用户的任何统计，也不产生真实的高光时刻 |

## 11. 专业体系（后期）

**产品决定（已确认）**：由团队内的健身实践者（项目负责人及其姐姐）后期专门建立一套专业体系，当前先用本文的大致方案。

### 11.1 需要专业校准的内容

| 内容 | 当前做法 | 后期 |
|---|---|---|
| 自重动作的体重系数 | 俯卧撑用文献值，其余用保守估计 | 逐个核对文献或实测 |
| 105 个动作的进步模型分类 | 按「复合 / 孤立 / 静力 / 自重」初分 | 逐个审核 |
| 进阶阶梯的家族与级别 | 俯卧撑、深蹲、引体三个家族先排 | 补全所有自重家族 |
| 肌群参与度 | 主动肌 1.0，协同肌粗估 | 参考肌电研究校准 |
| 噪声阈值、停滞参数 | 保守默认值 | 按训练水平分档 |
| 力量标准表 | 公开数据，标注「仅供参考」 | 替换为专业来源 |
| 健身规划（节奏、阶段、建议） | 不做 | 单独设计 |

### 11.2 设计上为此做的准备

- **所有系数和参数都是可配置的数据，不写死在逻辑里**：专业体系替换的是数据表，不是代码
- 进步计算是纯函数、不落库：校准后历史数据自动按新标准重算
- 数据层与规划层分离（§6.3）：健身规划上线时，数据层不需要改
